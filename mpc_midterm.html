011주차 · 병렬 컴퓨팅과 Hello CUDA

CPU는 반응 시간(latency), GPU는 처리량(throughput)을 노리고 설계됐다. CUDA는 GPU를 범용 병렬 보조 프로세서로 쓰게 해 주는 툴킷이고, 첫 프로그램은 for 반복문을 kernel<<<1,16>>>() 한 줄로 바꾼다.

1-0 오리엔테이션

시험과 평가 방식

시험 포인트 경북대 학생은 오프라인 시험(경북대 안의 별도 강의실, 시간·장소는 LMS 공지)을 본다. 형태는 closed book이다. 객관식이 일부 나올 수 있고, 주관식은 논술형·서술식이다. 서술형 답안은 상대 평가로 채점한다. 모든 답안을 가장 잘 쓴 것부터 가장 부족한 것·공백까지 한 줄로 정렬(global sorting)한 뒤 10점~1점, 0점을 준다.
  • 교수님 말씀: 한 줄만 쓰고 "맞는 답"이라고 주장해도 소용없다. 예년에 한 줄 답안은 잘해야 2점 정도였다. 상세하고 정확하게 써야 높은 점수를 받는다.
  • 오프라인 시험에 빠지면 학점이 나오지 않는다(녹취에서는 "아마 토요일"이라고 언급). DRU 등 외부 학생은 따로 안내하는 온라인 시험을 본다.
  • 평가(Relative Grading, 변동 가능): 중간 40~50%(→45%), 기말 40~50%(→45%), 숙제 2~10%(→5%), 출석·수업참여 2~10%(→5%).

강의 흐름과 실습 환경

과목은 multi-core CPU와 many-core GPU를 쓰는 병렬 컴퓨팅을 소개하고 CUDA(Compute Unified Device Architecture)를 익히는 과정이다. 선수 지식은 컴퓨터 구조(레지스터, 캐시, 폰 노이만 구조, 데이터 버스), 운영체제(time sharing, interrupt, device driver), 컴파일러(code generation, optimization)다.

주제 흐름: trends → CUDA 소개·설치 → data transfer → error check → CPU/CUDA kernel → 1D·2D kernel → matrix addition/multiplication → threads → elapsed time 측정 → memory hierarchy → adjacent differences → tiled matrix multiplication → DRAM 특성 → memory coalescing → bank conflict → atomic → reduction → 병렬 탐색·정렬(bitonic) → cuBLAS 등.

1-1 대규모 병렬 컴퓨팅 소개

CPU와 GPU

  • CPU(central processing unit, 중앙 처리 장치): 독립된 칩 하나(CPU chip). AMD, Intel, ARM 등.
  • GPU(graphics processing unit, 그래픽스 처리 장치): 기판 형태인 그래픽 카드(비디오 카드). NVIDIA, AMD(ex-ATI), Intel(CPU 내장) 등.
  • 강의는 GPU를 화면 출력 장치가 아닌 새로운 계산 기기(new computing device)로 본다.

왜 그래픽 카드였나: 1280×1024 화면 하나만 해도 픽셀이 100만 개가 넘는다. 화면을 그리려면 픽셀마다 계산해야 하므로, 그래픽 카드 회사들은 원래부터 100만 개 이상의 데이터를 병렬로 처리하는 데 익숙했다.

무어의 법칙과 병렬 컴퓨팅의 도입

무어의 법칙(Moore's law): IC 칩 하나에 들어가는 트랜지스터 수는 2년마다 2배가 된다(Gordon E. Moore, 전 Intel CEO). 트랜지스터가 늘어난 만큼 칩에 계산 유닛을 더 넣을 수 있게 되었다.

  • 코어(core) = 프로세서 안의 계산 유닛. ALU(arithmetic-logic unit)가 계산을, CU(control unit)가 ALU 제어를 맡는다.
  • 예전에는 싱글 코어 CPU였다. 2002~2003년 이후 멀티 코어 CPU(2~32+ cores)와 매니 코어 GPU(1,024~16,384+ cores)가 나왔다.

GPU 설계 철학: latency vs throughput

CPU와 GPU는 적용 분야가 다르다. CPU는 순차 처리(sequential processing)에 집중한다. 예를 들어 워드 프로세서는 키 하나를 누를 때마다 화면이 바로 반응해야 한다. GPU는 대규모 병렬 처리(massively parallel processing)에 집중한다. 빅데이터 통계처럼 대용량 입력을 한 번에 돌리고, 하나하나의 반응보다 전체가 다 처리되었는지가 중요하다.

시험 포인트 "CPU와 GPU의 설계 철학 차이를 설명하라"에는 목표(latency vs throughput), 코어(고성능·소수 vs 단순·다수), CU(코어마다 큰 CU vs CU 하나가 여러 ALU 제어), 캐시(대용량 vs 소규모), 적합한 작업(순차·대화형 vs 대규모 데이터 병렬)을 짝지어 쓴다. "GPU가 무조건 빠르다"가 아니라 문제가 대규모 병렬성을 가질 때 처리량이 커진다는 점을 덧붙인다.

MPC에 맞는 문제와 응용 분야

MPC = massively parallel computing(대규모 병렬 컴퓨팅). 가장 잘 맞는 문제는 계산 하나하나는 비교적 간단하지만(사칙연산, sin·cos 정도) 매우 대규모로 반복해야 하는 경우다. GPU의 ALU가 작고 단순한 대신 수가 많기 때문이다.

  • AI·딥러닝·머신러닝: 신경망의 핵심은 곱하기·더하기로 이루어진 거대한 행렬·벡터 계산이다. PyTorch, TensorFlow의 기반 기술이 MPC(특히 CUDA)다.
  • 암호화, 블록체인, 암호화폐: 단순 계산을 엄청나게 반복한다.
  • 과학·공학 시뮬레이션: 분자 생물학, 계산 생물학, 화학 분석, 기상 예측 등.

MPC 개발 도구

MPC에서 모델(model)은 프로그램 하나가 아니라 디바이스 + 프로그래밍 언어 + 컴파일러 + 라이브러리 + …의 묶음이다. 기존 언어는 순차 처리용이라, 병렬 처리를 표현하는 언어가 따로 필요하다. 보통은 C/C++를 병렬용으로 확장하고, 그 언어를 위한 컴파일러·라이브러리를 함께 제공한다.

1-2 CUDA 소개

CUDA란

  • CUDA = Compute Unified Device Architecture. 2006년 NVIDIA 전용으로 출시되었다.
  • 범용(general purpose) 프로그래밍 모델: GPU에서 대규모 스레드(thread)를 실행한다. 이로써 GPU의 용도가 화면 출력에서 대규모 병렬 처리 코프로세서(massively data parallel co-processor)로 넓어졌다.
  • GPU를 범용으로 쓰는 툴킷(toolkit): 디바이스·컴퓨터 구조 + 프로그래밍 언어 + 컴파일러 + much more.
    • CUDA 드라이버 → GPU 구동
    • CUDA 라이브러리 → API 함수들
    • CUDA 컴파일러 → 새로운(확장된) 프로그래밍 언어 사용 가능

그래픽 카드 안에 프로세서, 메모리, 캐시를 넣어 작은 컴퓨터처럼 만들고, 그 위에 병렬 언어·컴파일러·라이브러리를 풀 세트로 얹은 것이 CUDA다. 다양한 언어와 라이브러리를 제공하지만 가장 기본은 C/C++ API다.

FLOPS와 성능 비교

FLOPS = FLoating-point Operations Per Second. 1초당 부동소수점 연산 횟수로, 컴퓨터 성능 지표 중 하나다. TFLOPS = 1012 FLOPS(1조), PFLOPS = 1015 FLOPS(1,000조).

함정 RTX 5090의 104 TFLOPS(일반)와 1.676 PFLOPS(AI 학습 모드)는 계산 모드가 다른 수치다. 같은 조건의 성능처럼 섞어 비교하면 안 된다. 피크 FLOPS가 특정 프로그램의 실제 속도를 보장하는 것도 아니다.

1-3 Hello CUDA

Windows에서 첫 CUDA 프로그램

Visual Studio에서는 CUDA 샘플의 template 프로젝트를 복사해 쓰거나(바꿀 곳이 생각보다 많다), 새 프로젝트 → CUDA X.Y Runtime으로 만든다. 새 프로젝트의 kernel.cu에는 두 배열을 더하는 예제(addKernel에서 int i = threadIdx.x; c[i] = a[i] + b[i];)가 들어 있다. 강의는 이것을 지우고 가장 짧은 프로그램을 쓴다.

#include <cstdio>
__global__ void hello(void) {
    printf("hello, CUDA!\n");
}
int main(void) {
    hello<<<1,1>>>();   // GPU에서 스레드 1개로 실행
    return 0;
}
hello, CUDA!

CPU 반복문을 GPU 커널 launch로

같은 일을 하는 두 프로그램을 나란히 놓는다. CPU 쪽 for 반복문이 있던 자리를 GPU 쪽에서는 커널 실행 한 줄이 대신한다.

hello-cpu.cpp

void cpu_kernel(int idx) {
  printf("hello from CPU: idx=%d\n", idx);
}
int main(void) {
  printf("begin CPU kernel\n");
  for (int i = 0; i < 16; ++i) {
    cpu_kernel(i);
  }
  fflush(stdout);
  printf("end CPU kernel\n");
  return 0;
}

hello-gpu.cu

__global__ void kernel(void) {
  printf("hello from GPU: threadIdx.x=%d\n",
         threadIdx.x);
}
int main(void) {
  printf("begin GPU kernel\n");
  kernel<<<1,16>>>();   // for 반복문 자리
  cudaDeviceSynchronize();   // GPU 작업 완료 대기
  fflush(stdout);
  printf("end GPU kernel\n");
  return 0;
}
  • __global__: CUDA 함수(커널)임을 표시하는 설정자(specifier). GPU에서 병렬로 돌릴 함수라는 뜻이다.
  • triple chevron form(3중 꺽쇠 괄호) <<<1,16>>>: 커널을 실행(launch)하는 문법이다. 강의 표현으로 1 × 16 = 16개 core를 써서 함수를 동시에 실행한다.
  • threadIdx.x: 커널 안에서 쓰는 내장 변수. 각 스레드가 자기 번호를 얻는다. 모든 스레드가 같은 함수 본문을 실행하지만, 번호가 달라 서로 다른 출력·데이터를 맡는다. CPU 버전의 idx 인자 역할이다.

.cu 확장자와 컴파일

.cu는 CUDA 프로그램의 확장자다. .cu 파일 = .cpp 파일(C/C++) + CUDA 커널 소스 코드로, host 코드와 커널이 한 파일에 함께 들어간다. 컴파일은 nvcc(NVIDIA CUDA Compiler)가 한다.

그렇다면 C/C++ 코드만 담은 hello-cpp.cu도 될까? 된다. .cu는 CUDA 커널을 포함시킬 수 있다는 뜻이지 꼭 포함해야 한다는 뜻은 아니다. 다만 관례상 .cu에는 __global__ 커널이 들어 있다고 보는 것이 헷갈리지 않는다.

실행 구성: <<<1,16>>>와 <<<4,4>>>

hello-gpu.cu에서 launch 줄만 kernel<<<4,4>>>();로 바꾸면 4 × 4 = 16번이 실행된다. 강의 표현으로 "함수를 4세트, 4개 core씩 동시 실행"이고, 이것이 병렬 컴퓨팅이다. 총 실행 횟수는 같지만 threadIdx.x는 각 세트(블록) 안에서의 번호라서 0~3이 네 번 반복된다. 두 방식의 차이는 이후 강의에서 블록·스레드 개념으로 다룬다.

begin GPU kernel hello from GPU: threadIdx.x=0 hello from GPU: threadIdx.x=1 hello from GPU: threadIdx.x=2 hello from GPU: threadIdx.x=3 hello from GPU: threadIdx.x=0 hello from GPU: threadIdx.x=1 hello from GPU: threadIdx.x=2 hello from GPU: threadIdx.x=3 hello from GPU: threadIdx.x=0 hello from GPU: threadIdx.x=1 hello from GPU: threadIdx.x=2 hello from GPU: threadIdx.x=3 hello from GPU: threadIdx.x=0 hello from GPU: threadIdx.x=1 hello from GPU: threadIdx.x=2 hello from GPU: threadIdx.x=3 end GPU kernel

위는 <<<4,4>>>의 실행 결과다. <<<1,16>>>는 0부터 15까지 한 번씩 나온다. 슬라이드의 실행 화면에는 "hello from GPU kernel: …"으로 찍혀 있어 코드 문자열과 조금 다르다. CPU 쪽 실행 결과는 begin CPU kernel → idx=0~15 → end CPU kernel이다.

함정 강의 실행에서는 출력이 정렬되어 나왔지만, 병렬 실행이므로 세트(블록) 사이의 실행 순서는 보장되지 않는다. 또 "1×16 = 16개 core 사용"은 입문용 직관적 표현이다. 실제로는 스레드 16개를 요청한 것이고, 물리 코어에 어떻게 배치되는지는 이후에 배운다.

CUDA 함수 규칙과 cudaDeviceSynchronize

  • 모든 CUDA 함수는 cuda로 시작한다.
  • 대부분은 에러 코드를 리턴하고, 성공 시 값은 cudaSuccess다. 그래서 반환값을 바로 비교할 수 있다.
if ( cudaMalloc( &devPtr, SIZE ) != cudaSuccess ) {
    exit(1);
}
cudaError_t cudaDeviceSynchronize( void );

모든 CUDA device가 주어진 일을 완료(finish)할 때까지 기다린다. 원문은 "Blocks until the device has completed all preceding requested tasks."이고, 반환값은 cudaSuccess다. 이 함수가 돌아왔다는 것은 앞서 요청한 커널 등이 완벽히 끝났다는 보장이다.

시험 포인트 교수님 강조: 커널을 불렀으면 반드시 cudaDeviceSynchronize()를 써라. 이후 예제들도 triple chevron으로 커널을 실행한 뒤 바로 동기화해서 완료를 보장한 다음 결과를 본다. 반면 fflush(stdout)은 CPU 쪽 printf 출력 버퍼를 비우는 것으로, GPU 동기화와 역할이 다르다.

device 코드에서는 C++ stream이 안 된다

#include <iostream>
__global__ void kernel(void) {
    std::cout << "hello from GPU" << std::endl;   // 컴파일 에러
}
error: identifier "std::cout" is undefined in device code

커널 함수 안에서는 C++ 스트림(std::cout)을 지원하지 않는다. C++의 온갖 클래스를 GPU에서 모두 지원하기는 무리이기 때문이다. 대신 C의 printf는 되므로 커널 출력은 printf로 쓴다.

2-1 정적 배열 (Static Arrays)

host와 device: 분리된 두 메모리

PC 본체(호스트)에는 CPU와 메인 메모리가, 그래픽 카드(디바이스)에는 GPU와 비디오 메모리가 있습니다. 둘은 PCI Express 슬롯으로만 이어져 있습니다. 강의에서는 이름을 섞어 쓰지만, 결국 가리키는 것은 두 영역뿐입니다.

구분구성같은 뜻으로 쓰는 이름
호스트 hostCPU + main memorymain memory, RAM, CPU memory, host memory
디바이스 deviceGPU + video memoryvideo memory, graphics memory, VRAM, GPU memory, CUDA memory, device memory

CUDA 프로그래밍 모델은 이 구조를 그대로 따릅니다. CPU는 main memory만, GPU는 video memory만 직접 씁니다. CPU ↔ video memory, GPU ↔ main memory는 기판상 직접 연결 불가입니다. 그래서 자료가 필요하면 PCIe를 거쳐 명시적으로 복사해야 합니다.

노트북은 CPU와 GPU가 한 기판에 있어서 물리적으로는 main memory 하나를 공유하기도 합니다. 그래도 OS가 일부를 잘라 "여기는 GPU 전용 video memory"로 경계를 정해 줍니다. 그래서 CUDA는 개념적으로는 항상 두 영역을 구분하는 모델을 씁니다.

쉽게 말하면 CPU와 GPU는 각자 자기 책상(메모리)에서만 일합니다. 남의 책상에 있는 서류는 손이 닿지 않으니, 복도(PCIe)를 통해 복사본을 건네줘야 합니다.

CUDA 컴파일러(NVCC)의 구조

NVCC를 설치하기 전에 clang·gcc·msvc 같은 C++ 컴파일러를 먼저 깔아야 했던 이유가 여기 있습니다. NVCC는 .cu 소스를 두 부분으로 나눕니다.

  • CUDA 커널 코드(__global__ 등): NVCC가 직접 컴파일 → GPU용 실행 코드
  • 순수 C++ 코드(main 등): 설치된 C++ 컴파일러에 넘김 → CPU용 실행 코드
  • 두 결과를 하나의 실행 파일에 함께 넣고, 실행할 때 나눠서 CPU와 그래픽 카드로 보낸다
시험 포인트 "nvcc 명령만 썼는데 C++ 코드가 어떻게 컴파일되나?" → NVCC가 소스를 커널 부분과 순수 C++ 부분으로 분리하고, C++ 부분은 미리 설치된 C++ 컴파일러를 내부적으로 호출해 컴파일한다. 두 실행 코드는 하나의 실행 파일로 합쳐진다.

CUDA 커널과 프로그램 시나리오

CUDA 커널은 GPU가 실행하는 작은 (병렬) 프로그램이고, 주로 video memory를 씁니다. 커널에서는 I/O 장치 사용이 제한됩니다. 하드디스크의 데이터는 main memory까지만 올라오기 때문에, GPU가 쓰려면 한 번 더 video memory로 옮겨야 합니다. 그래서 전형적인 CUDA 프로그램은 다음 3단계를 거칩니다.

단계실행 주체하는 일
step 1호스트 CPU외부 데이터(파일, scanf) → main memory, 그리고 main memory → video memory 복사
step 2커널 (디바이스)video memory의 데이터를 GPU가 병렬 처리, 결과도 video memory에 저장
step 3호스트 CPUvideo memory → main memory 복사 후 printf 출력·파일 저장

그래픽 카드 안에는 GPU 프로세서(코어)가 수천 개 있고, 이들이 video memory를 함께 씁니다. 그래서 video memory를 글로벌 메모리(global memory)라고도 부릅니다.

분리된 메모리 공간과 __device__ 선언

  • video memory 할당·복사: 반드시 별도의 CUDA 함수 사용
  • main memory 할당·복사: C++ 함수도 가능하지만 CUDA 함수 권장
  • 배열 선언 위치: 일반 배열 선언 → main memory / __device__가 붙은 배열 → video memory

예제: 벡터-스칼라 더하기 (vec-inc-static.cu)

길이 n인 벡터(1D 배열) A의 모든 원소에 스칼라 X를 더해 C에 저장합니다: C[i] = A[i] + X. N = 1024이고, 원소 하나를 스레드 하나가 맡습니다.

위치선언·코드
main memoryconst int N = 1024; · float A[N]; · float C[N];
device memory__device__ float devA[N]; · __device__ float devC[N];
kernel programdevC[i] = devA[i] + X;
const int N = 1024;
float A[N];                  // host memory (main memory)
float C[N];
__device__ float devA[N];     // device memory (graphics memory)
__device__ float devC[N];

__global__ void kernel_inc(const float X) {
    int i = threadIdx.x;
    devC[i] = devA[i] + X;
}
int main(void) {
    for (int i = 0; i < N; ++i) A[i] = (float)i;   // CPU part
    printArray(N, A);
    cudaMemcpyToSymbol(devA, A, sizeof(A));          // copy A to devA
    kernel_inc<<<1, N>>>(1.0);                       // GPU part
    cudaDeviceSynchronize();
    cudaMemcpyFromSymbol(C, devC, sizeof(C));        // copy devC to C
    printArray(N, C);
    return 0;
}

printArray는 앞 4개와 뒤 4개만 %10.3f로 찍고 가운데는 . . .로 줄입니다. 첫 줄은 A, 둘째 줄은 커널을 거친 C입니다.

0.000 1.000 2.000 3.000 . . . 1020.000 1021.000 1022.000 1023.000 1.000 2.000 3.000 4.000 . . . 1021.000 1022.000 1023.000 1024.000
함정 커널은 devA, devC를 인자로 받지 않고 전역 __device__ 배열 이름을 직접 씁니다. 커널은 비동기로 실행되므로 결과를 가져오기 전에 cudaDeviceSynchronize()로 끝날 때까지 기다려야 합니다.

symbol 복사 함수: cudaMemcpyToSymbol / FromSymbol

CUDA에서 symbol은 CUDA 메모리(device)에 있는 변수의 이름을 뜻합니다. 위 예제의 devA, devC가 바로 symbol입니다.

cudaError_t cudaMemcpyToSymbol(void* symbol, const void* src, size_t nbytes);
cudaError_t cudaMemcpyFromSymbol(void* dst, const void* symbol, size_t nbytes);
  • ToSymbol: main memory(src) → symbol이 가리키는 device 영역. symbol 자리에는 __device__로 선언된 변수(의 주소)가 들어간다
  • FromSymbol: symbol이 가리키는 device 영역 → main memory(dst)
  • nbytes = 복사할 byte 수. 그래서 원소 수 N이 아니라 sizeof(A) = 1024 × 4 = 4096을 넘긴다
  • 방향은 함수 이름(To/From)으로 정해진다. C의 memcpy와 비슷하지만 CUDA 변수 이름을 넣는다는 점이 다르다

ROCm(AMD GPU)에서 실행

  • 변환: hipify-perl -o vec-inc-static.hip vec-inc-static.cu (warning이 일부 나올 수 있음)
  • 컴파일: hipcc vec-inc-static.hip -Wno-unused-value. 이 옵션은 hipcc가 내는 많은 warning을 끄는 용도이고, 실행 결과는 CUDA와 같다
  • 변환된 코드에서 symbol 인자는 HIP_SYMBOL()로 감싸진다: hipMemcpyToSymbol(HIP_SYMBOL(devA), A, sizeof(A)); · cudaDeviceSynchronize → hipDeviceSynchronize
2-2 동적 메모리 할당 (Dynamic Allocation)

주소 문제와 dev_ 접두사

메모리를 할당하면 주소(포인터)를 받습니다. 그런데 포인터 값만 봐서는 그 주소가 main memory 것인지 video memory 것인지 알 수 없습니다. 커널에는 반드시 video memory 주소가, printf 같은 host 코드에는 main memory 주소가 와야 하고, 반대쪽 주소를 넣으면 error가 납니다. 이 구별은 프로그래머의 책임입니다.

쉽게 말하면 주소만 적힌 쪽지로는 그게 집 주소인지 회사 주소인지 모릅니다. 그래서 CUDA 프로그래머들은 device 쪽 포인터·변수 이름 앞에 dev_(또는 dev)를 붙여 한눈에 구별합니다. 컴파일러를 위한 게 아니라 사람을 위한 관례입니다.

C 메모리 함수와 CUDA 메모리 함수

C/C++의 함수는 main memory를 다루고, CUDA는 같은 역할을 하는 video memory용 함수를 따로 제공합니다. 매개변수 이름은 nbytes ← number of bytes, ptr ← pointer, dst ← destination(목적지), src ← source(원천), num ← number의 줄임입니다.

역할C/C++ (main memory)CUDA (video memory)
할당void* malloc(size_t nbytes);cudaError_t cudaMalloc(void** dev_ptr, size_t nbytes);
해제void free(void* ptr);cudaError_t cudaFree(void* dev_ptr);
값 설정void* memset(void* ptr, int value, size_t count);cudaError_t cudaMemset(void* dev_ptr, int value, size_t count);
복사void* memcpy(void* dst, const void* src, size_t num);cudaError_t cudaMemcpy(void* dst, void* src, size_t nbytes, cudaMemcpyKind direction);
int* dev_ptr = nullptr;
cudaMalloc((void**)&dev_ptr, nbytes);   // 주소를 반환값이 아니라 인자로 받는다
cudaMemset(dev_ptr, 0, nbytes);
cudaFree(dev_ptr);
시험 포인트 int* dev_ptr을 main()에서 선언하면 변수 자체는 main memory에 있고, cudaMalloc 후 그 값이 video memory 영역의 시작 주소가 됩니다. 그래서 host 코드에서 dev_ptr[0]처럼 역참조하면 안 됩니다. 남의 메모리 주소이기 때문입니다.

cudaMalloc · cudaFree · cudaMemset

모든 CUDA 함수는 cuda로 시작하고, 거의 대부분 에러 코드(성공하면 cudaSuccess)를 반환합니다. 반환값 자리를 에러 코드가 차지하니까, 주소처럼 돌려줘야 할 값은 인자로 받은 포인터 안에 써 줍니다. 그래서 cudaMalloc은 포인터 변수의 주소 &dev_ptr을 (void**)로 받습니다.

if (cudaMalloc(&devPtr, SIZE) != cudaSuccess) { exit(1); }
함수동작리턴 값
cudaMalloc(void** devPtr, size_t nbytes)video memory에 nbytes 할당, 시작 주소를 devPtr에 저장. 메모리는 clear하지 않음cudaSuccess, cudaErrorMemoryAllocation
cudaFree(void* devPtr)devPtr이 가리키는 메모리 반환. devPtr == nullptr 또는 0이면 무시cudaSuccess, cudaErrorInvalidDevicePointer
cudaMemset(void* devPtr, int value, size_t nbytes)처음 nbytes를 value로 설정. byte 단위cudaSuccess, cudaErrorInvalidValue, cudaErrorInvalidDevicePointer
함정 cudaMemset은 byte 단위로 채웁니다. value = 0이면 모든 byte가 0이라 깔끔하게 clear되지만, value = 0x77이면 모든 byte가 0x77이 되어 4-byte int 하나는 0x77777777이 됩니다. int 원소마다 0x77을 넣는 게 아닙니다. 그래서 memset은 주로 0으로 지우는 용도로만 씁니다.

cudaMemcpy와 복사 방향

cudaError_t cudaMemcpy(void* dst, void* src, size_t nbytes, enum cudaMemcpyKind direction);
  • C의 memcpy와 같지만 마지막에 방향(cudaMemcpyKind)을 꼭 적어야 한다. memcpy는 host 안에서만 움직였지만, CUDA는 src와 dst가 각각 어느 메모리 주소인지 알아야 하기 때문이다
  • 이전 CUDA 함수들이 모두 끝나야 복사가 시작되고, 복사 중에는 CPU 스레드도 멈추며, 완료되어야 리턴한다 (동기식)
  • 이름 규칙: host = CPU, main memory, RAM / device = CUDA, video memory, VRAM

vec-inc-alloc.cu: 배열 선언을 할당으로 바꾸기

문제는 2-1과 똑같이 C[i] = A[i] + X입니다. 달라진 것은 그릇입니다. 배열을 선언하는 대신 포인터만 만들어 두고, 실행 중에 공간을 할당합니다. 커널은 전역 배열 이름 대신 포인터를 인자로 받습니다.

함정 크기는 byte 수입니다. 동적 할당에는 sizeof(A)를 쓸 수 없으므로 N * sizeof(float)를 써야 합니다. 포인터에 sizeof(ptrA)를 쓰면 포인터 크기(8)만 나옵니다.

cudaMallocHost와 cudaFreeHost

cudaError_t cudaMallocHost(void** ptr, size_t nbytes);   // main memory에 할당
cudaError_t cudaFreeHost(void* ptr);                    // cudaMallocHost로 받은 메모리 해제

이름에 Host가 붙은 그대로 main memory에 nbytes를 할당합니다. 시작 주소를 ptr에 저장하고, clear하지 않으며, 리턴 값은 cudaSuccess / cudaErrorMemoryAllocation으로 cudaMalloc과 같습니다. 이렇게 잡은 메모리를 page-locked 메모리라고 합니다. 그러면 malloc과 무엇이 다를까요?

malloc

할당한 영역을 OS가 관리합니다. CUDA는 이 영역을 쓰기만 할 뿐 관리하지 못합니다.

cudaMallocHost

할당한 영역을 CUDA가 직접 관리하고, OS에 절대 빼앗기지 않습니다. 그래서 CUDA는 최대 효율로 쓸 수 있지만, OS는 메모리를 빼앗긴 셈이라 OS 성능이 떨어질 수 있습니다.

vec-inc-malloc-host.cu는 vec-inc-alloc.cu에서 malloc 두 줄만 cudaMallocHost((void**)&ptrA, N * sizeof(float));로 바꾼 것이고, 결과는 같습니다. 1024 × 4 byte 정도는 OS에 영향이 없습니다. 메인 메모리의 절반 이상을 빼앗는 정도가 되어야 문제가 됩니다. 그래서 강의 예제에서는 앞으로 가능하면 cudaMallocHost를 씁니다.

시험 포인트 "malloc이 있는데 cudaMallocHost가 왜 필요한가?" → 효율성. CUDA가 host 메모리 영역을 직접 관리(page-locked)하므로 CUDA 입장에서 최대 효율로 쓸 수 있다. 대가로 OS는 그 영역을 다른 프로그램에 줄 수 없어 전체 성능이 떨어질 수 있다. 해제는 반드시 cudaFreeHost로 한다.

통합 메모리 (Unified / Managed Memory)

포인터마다 어느 쪽 메모리인지 함수로 확인하는 건 비효율적이라 보통 dev_ 접두사로 구별합니다. 그런데 노트북처럼 물리적으로 메모리가 붙어 있으면 굳이 접근을 막을 이유가 없습니다. 그래서 등장한 것이 unified memory system입니다.

  • CPU와 GPU 양쪽에서 모두 쓸 수 있는 메모리 영역을 할당한다
  • 하드웨어와 OS가 지원해야 쓸 수 있다
  • 필요하면 CUDA가 알맞은 영역으로 자동 복사해 준다 (데스크톱에서는 H→D, D→H 자동 이동)

장점

memory copy를 프로그래머가 직접 할 필요가 없습니다. 코드가 매우 간결해집니다.

단점

필요할 때마다 CUDA가 복사하므로 느려질 수 있습니다. 프로그래머가 모르는 사이에 복사가 빈번하게 일어나 큰 배열이 왔다 갔다 하며 시간만 낭비할 수 있습니다.

cudaMallocManaged와 cudaMemAdvise

cudaError_t cudaMallocManaged(void** devPtr, size_t size,

  • cudaMallocManaged: unified memory system에서 자동 관리(automatically managed)되는 size byte 이상의 영역을 할당하고 시작 주소를 *devPtr에 돌려준다
  • 시스템이 managed memory를 지원하지 않으면 cudaErrorNotSupported. 그래서 반환값 검사가 꼭 필요하다
  • flags: 기본으로 어디에 둘지 지정한다. cudaMemAttachGlobal(device에 할당, 기본값) 또는 cudaMemAttachHost(host에 할당)
  • 해제는 cudaFree()로 한다 (cudaFreeHost가 아니다)
  • cudaMemAdvise: devPtr부터 count byte 영역이 어떻게 쓰일지 미리 알려 주는 힌트(advice). 자주 쓰는 조합은 아래 4가지

CUDA 컴파일러 구조와 컴파일 단위

.cu 파일 하나에는 GPU가 실행할 코드와 CPU가 실행할 코드가 섞여 있습니다. nvcc(NVIDIA CUDA Compiler)는 이 중 CUDA kernel code만 직접 GPU 실행 코드로 만들고, 나머지 pure C++ code는 clang / gcc / msvc 같은 일반 C++ 컴파일러에 넘겨 CPU 실행 코드로 만들게 합니다.

그래서 nvcc는 "어느 부분이 CUDA가, 어느 부분이 CPU가 처리할 부분인가?", 즉 컴파일 단위(unit of compilation)를 정해야 합니다. 후보는 두 가지가 있었습니다.

후보예CUDA의 선택
파일 단위C/C++ 컴파일러의 기본 처리함수(function) 단위. 각 함수가 CPU 또는 GPU(또는 둘 다)에 배정된다
라인 단위C/C++의 asm 처리 방식

함수 한정자: __host__ · __global__ · __device__

함수마다 담당 컴파일러를 구별하려고 함수 앞에 prefix를 붙입니다. 앞뒤의 __는 밑줄(underscore) 두 개입니다.

한정자의미called byexecuted on
__host__일반 C/C++ 함수, CPU 처리. default라 생략 가능hosthost
__global__CUDA kernel 함수. CPU에서 시작, GPU가 처리. 반드시 void 반환hostdevice
__device__CUDA 내부용 함수, GPU 처리devicedevice

강의 예제(atomicCAS로 만든 덧셈)는 세 한정자가 한 파일에 같이 쓰이는 모습을 보여 줍니다.

__device__ inline void myAtomicAdd(unsigned long long int* address, unsigned long long int val) { ... atomicCAS ... }
__global__ void kernel(unsigned long long int* pCount) {
    myAtomicAdd(pCount, 1ULL);      // GPU 코드가 __device__ 함수 호출
}
__host__ int main(void) { ... }      // __host__는 생략해도 같다
쉽게 말하면 __global__은 CPU와 GPU 사이의 "현관문"입니다. CPU는 이 문으로만 GPU에 일을 넘기고(실행 권리를 넘기고 기다리거나 다른 일을 함), GPU 안에서는 __device__ 함수들을 자유롭게 부릅니다.

CUDA 언어의 특징과 제약

CUDA 언어 = C/C++ + 몇 가지 제약(some restrictions). 주로 GPU memory(CUDA memory, video memory)를 사용하고, host memory를 쓰면 성능 손해(performance drawbacks)가 납니다. __device__ / __global__ 함수에는 다음 제약이 있습니다.

제약이유 (강의 설명)
함수의 address를 가져올 수 없음 (함수 포인터 X)CUDA가 설계상 막아 둠
함수 내부에 static 변수 선언 불가100만 개가 동시에 실행되면 static 변수도 100만 개를 device 메모리에 잡아야 해서 의미가 없음. 필요하면 별도 배열이나 constant를 쓴다
재귀 호출(recursion)은 되도록 사용하지 않음옛 버전은 아예 금지. 지금은 컴파일되지만 잘못 쓰면 효율이 급격히 떨어짐

벡터 덧셈과 kernel 함수의 도입

벡터는 n개 원소의 1D array로 표현하고, 원하는 연산은 원소끼리의 덧셈 C[i] = A[i] + B[i]입니다.

CPU는 이것을 순차 처리(sequential execution), 즉 for loop로 구현합니다. 커널 함수로 가는 핵심 아이디어는 loop body를 별도의 함수로 대체하고, 필요한 data는 파라미터로 전달하는 것입니다.

__host__ void kernel_cpu_vec_add(int idx, float* C, const float* A, const float* B) {
    int i = idx;
    C[i] = A[i] + B[i];
}

Kernel 함수의 해석: 순차 → 병렬 → 대규모 병렬

loop body를 함수로 떼어 내면, "누가 몇 번째 호출을 언제 실행하느냐"만 바꿔서 같은 함수를 병렬로 돌릴 수 있습니다.

CPU kernels

단일 CPU 코어 · for-loop · sequential execution. CPU at time 0, 1, 2, …, (n−1).

GPU kernels

GPU 코어 집합 · multiple threads · parallel execution. kernel launch! → GPU core #0, #1, …, #(n−1)이 동시에.

Kernel launch와 threadIdx.x

C/C++ 함수 호출이 "전화 걸기"라면 CUDA kernel launch는 "로켓 발사"입니다. for 루프로 N번 부르던 것을 한 번의 launch로 N개를 동시에 출발시킵니다. 표기는 triple chevron(3중 꺾쇠) <<< , >>>로, C/C++에서 쓰지 않는 연산자라서 골랐습니다.

__global__ void kernel(float* C, const float* A, const float* B) {
    int i = threadIdx.x;      // launch 때 자동 설정되는 thread index
    C[i] = A[i] + B[i];
}
kernel<<<1, N>>>(devPtrC, devPtrA, devPtrB);
시험 포인트 CPU 커널과 GPU 커널의 차이는 본문 단 한 줄입니다. CPU 버전은 int i = idx;로 인덱스를 인자로 받고 반복문이 순차 호출하지만, GPU 버전은 int i = threadIdx.x;로 launch 때 자동 설정된 자기 스레드 번호를 씁니다. 그래서 GPU 커널에는 인덱스 파라미터와 for 루프가 없습니다.

3-2 Error 체크

cudaError_t와 오류 문자열 함수

CUDA 함수 규칙: 모든 CUDA 함수는 cuda로 시작하고, (커널을 제외한) 대부분은 error code를 리턴합니다. 성공하면 cudaSuccess.

if (cudaMalloc(&devPtr, SIZE) != cudaSuccess) {
    exit(1);
}

오류 코드의 자료형은 typedef enum cudaError cudaError_t입니다. 값은 cudaSuccess, cudaErrorMemoryAllocation, cudaErrorInvalidValue, cudaErrorInvalidSymbol, cudaErrorLaunchFailure, cudaErrorInvalidConfiguration, cudaErrorInvalidMemcpyDirection, … 등입니다. 숫자 코드를 외울 수 없으니 문자열로 바꾸는 함수 두 개가 있습니다.

함수돌려주는 것err = cudaErrorMemoryAllocation일 때 출력

const char* cudaGetErrorString(cudaError_t err)사람이 읽는 설명(explanation)out of memory

둘 다 NULL-terminated string을 가리키는 const char*를 돌려주고, 코드가 유효하지 않으면 NULL / nullptr를 돌려줍니다.

last error 플래그: Get과 Peek

CUDA runtime은 내부에 last error라는 flag 변수를 하나 둡니다. API 함수가 실패하면 오류 코드를 리턴하는 동시에 last error에 그 원인을 기록합니다. 또 실패하면 덮어씁니다. 성공한 호출은 last error를 건드리지 않습니다.

함수반환last error 초기화
cudaError_t cudaGetLastError(void)같은 host thread의 runtime 호출로 생긴 마지막 오류reset → cudaSuccess. 그래서 지난 호출 이후 오류가 없으면 cudaSuccess
cudaError_t cudaPeekAtLastError(void)마지막 오류reset하지 않음. 오류 코드가 계속 남아 있음
쉽게 말하면 peek은 "엿보다". 발생 여부 확인은 Peek으로, 실제로 꺼내서 처리할 때는 Get으로 하는 게 일반적입니다. last error는 마지막 1개만 기억하므로 오류 체크를 자주, 가까운 위치에서 해야 합니다.

오류 상태는 CPU thread 단위

cudaGetLastError는 "in the same host thread"의 마지막 오류를 돌려줍니다. CPU 쪽이 멀티스레드로 돌면서 스레드마다 CUDA 커널을 부르면, CUDA는 CPU thread마다 별도의 error 상태를 관리합니다.

강의 예제는 CPU 스레드가 1개라서 error flag도 하나만 다룹니다.

  • 대부분의 C/C++ 컴파일러는 debug mode에 _DEBUG, release mode에 NDEBUG를 정의합니다. debug mode에서는 오류를 체크하고 친절하게 출력하고, release mode에서는 매크로가 0;이 되어 아무 일도 하지 않습니다(체크를 빼서 약간 빨라짐).
  • 이 매크로는 ./common.cpp에 추가해 두고 씁니다. 슬라이드 메모: "실제 코드는 항상 체크".

        }

    }
    return num;                               // 인자가 없거나 0 이하면 기본값
}

time sharing과 parallel processing

코어가 하나뿐이면 여러 스레드를 조금씩 번갈아 실행해 동시에 도는 것처럼 보이게 한다. 이것이 time sharing이다. 목표는 가장 비싼 자원인 processor가 쉬지 않게 해서 최고 효율을 내는 것이다. 즉 할 일이 있는데 CPU가 놀면 안 된다.

running 중인 스레드가 I/O나 메모리 접근을 기다려야 하면 waiting으로 보내고 ready에 있던 다른 스레드를 dispatch한다. 기다림이 끝나면 다시 ready로 간다. 메모리 대기를 다른 스레드로 메우는 이 아이디어는 GPU에서도 그대로 쓰인다(아래 SM 설명).

CUDA 프로그래밍 모델: 계층적 launch

  • parallel code(kernel)는 device에서 many threads로 launch·실행된다. multiple threads가 ~10개라면 many threads는 1,000개 이상이고, 실제로는 1M+개다.
  • many-core GPU는 1,000개 이상(실제로는 10K+) 코어를 가진다. multi-core CPU는 10개 안팎이다.
  • 보통 thread 개수 ≫ core 개수다. 데이터가 1G~1T items로 크기 때문이다(예: 1,000,000 threads on 1,000 cores).
  • 그래서 launch는 계층적이다. grids – blocks – threads: thread를 묶어 block, block을 묶어 grid를 만든다.
  • 각 thread 안은 익숙한 sequential code이고 thread 전체는 parallel로 실행된다. 자기 위치는 built-in thread·block ID 변수로 안다.
쉽게 말하면 코어가 만 개인데 일거리는 십억 개다. 그래서 일거리를 "반(block)" 단위로 묶어 두고, 비는 교실(SM)이 생길 때마다 한 반씩 들여보낸다. 학생(thread) 한 명이 하는 일은 평범한 순차 코드다.

커널 선언·호출과 dim3

kernel function은 정해진 규약대로 선언하고 불러야 한다. 선언은 독립적인 함수 형태로 하고, 호출은 __host__ function에서 triple chevron으로 한다.

__global__ void kernel_func( ... ) { ... }

kernel_func<<< dimGrid, dimBlock >>>( ... );   // 1번째 = grid당 block 수, 2번째 = block당 thread 수
kernel_func<<< 8, 16 >>>( ... );               // 8 blocks × 16 threads

grid와 block 구조는 최대 3차원이다. 1D는 1차원 배열, 2D는 행렬·영상, 3D는 3차원 그래픽 자료에 쓴다. grid는 kernel마다 1개이며, grid dimension은 내부 block 배치이고 block dimension은 내부 thread 배치다. block과 thread는 각각 (x, y, z) index(ID)를 가진다.

vector type, uint3와 dim3

  • CUDA는 char1~4, uchar, short, ushort, int, uint, long, ulong, float1~4, longlong, ulonglong, double1~4 같은 vector type을 제공한다. 성분은 .x .y .z .w로 접근하고, 생성자는 make_float4(x, y, z, w)(__host__ __device__)다.
  • uint3와 dim3는 둘 다 unsigned int x, y, z를 가진 class이고, char1은 typedef char char1;일 뿐이다. kernel launch용 dim3는 반드시 이 x, y, z 형태를 가진다.

__global__ void kernel( int* a, int dimx ) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;   // 2 * 4 + 3 = 11
    if (idx < dimx) {
        a[idx] = a[idx] + 1;
    }
}

gridDim(6)이면 blockIdx는 0~5, blockDim(4)이면 threadIdx는 0~3이다. (blockIdx, threadIdx) 쌍은 thread마다 unique하므로 위 식으로 겹치지 않는 전역 번호를 얻는다. 앞 블록들이 쓴 스레드 수(blockIdx.x × blockDim.x)에 블록 안 번호를 더하는 식이다. 대부분의 커널은 시작하자마자 이 계산을 한다.

함정 threadIdx.x만 인덱스로 쓰면 모든 블록이 0~3번 원소만 처리한다. 블록마다 threadIdx는 다시 0부터 시작하기 때문이다. 또 곱하는 값은 gridDim.x가 아니라 blockDim.x(블록 하나의 크기)다.

2D에서는 같은 계산을 x, y 각각에 한 번씩 하면 된다. 2D 인덱스 계산은 5주차 행렬 연산에서 본격적으로 쓴다.

CUDA 아키텍처: SP, SM, thread block queue

SP (streaming processor)

thread 하나를 실행한다. ALU 정도의 낮은 성능이며 "core"라고도 부른다. 레지스터를 갖고 global memory(video memory)에 접근한다.

SM (streaming multi-processor)

thread block 하나를 맡는다. ALU들 + CU(control unit)로 구성되고, SP의 집합(예: 32개)이며 per-block shared memory와 많은 레지스터를 가진다.

  • 주의할 점은 SP·SM에서도 time sharing이 일어난다는 것이다. 그래서 최대 효율이 나오도록 설계한다.
  • 해결책은 zero context switching이다. thread 전환 비용이 거의 없다. 비결은 레지스터를 매우 많이 할당해 각 thread의 상태를 레지스터에 그대로 두는 것이다(예: 64K registers per SM).
  • thread block = many threads(예: 1024)이지만 SM은 한 번에 32개 thread만 실제로 실행한다. 나머지 대부분은 대기하다가, 실행 중인 스레드가 메모리를 기다리면 즉시 교체되어 들어간다.
  • SM의 물리적 한계 = thread block의 최대 크기다. 현재 CUDA는 block당 최대 1,024 threads다. 블록 하나가 SM 하나에 통째로 올라가야 하기 때문이다.
  • CUDA device = many SMs이고 (thread block 개수 ≫ SM 개수)다. 블록은 queue에서 하나씩 꺼내져 비어 있는 SM에 할당된다.

이 queue는 엄밀한 FIFO 큐도, 정확한 우선순위 큐도 아닌 queue-like 구조다. 요구 사항은 "블록들을 저장하고, 하나씩 가져가서 실행하고, 제거"하는 것뿐이고, 정확한 우선순위는 필요하지도 계산할 수도 없다. 그래서 느슨한 자료구조로 충분하다. 결과적으로 블록 실행 순서는 보장되지 않는다.

시험 포인트 서술형 예시: "block 크기에 상한(1,024)이 있는 이유는?" 답은 이렇다. 한 블록은 한 SM에 배정되어 그 SM의 레지스터·shared memory 안에서 실행되므로, SM의 물리적 한계가 곧 블록의 최대 크기가 된다. "GPU의 time sharing이 CPU보다 효율적인 이유는?" 답은 zero context switching이다. 레지스터가 충분해 thread 상태를 저장·복원할 필요가 없다.

launch 크기 계산과 boundary check

  • 전체 thread 개수 = dimBlock.x * dimGrid.x ≥ N을 보장해야 한다.
  • block dim은 최대 1,024다. 최적화 관점에서 하드웨어 한계까지 쓰는 게 보통이라 dim3 dimBlock(1024, 1, 1)로 둔다.
  • grid dim = ⌈N / block dim⌉(올림 연산)이다. 내림하면 N보다 적은 스레드가 만들어져 뒷부분이 계산되지 않는다.
  • N = 1G의 1D layout이면 dimBlock.x = 1,024 = 1K threads per block이고, dimGrid.x = 1G / 1K = 1M thread blocks다.
dim3 dimBlock(1024, 1, 1);
dim3 dimGrid((N + dimBlock.x - 1) / dimBlock.x, 1, 1);   // 정수 나눗셈으로 올림
kernel_vec_add<<< dimGrid, dimBlock >>>(devPtrC, devPtrA, devPtrB, N);
cudaDeviceSynchronize();   // 비동기 launch가 끝날 때까지 기다린 뒤 end 시각 측정
CUDA_CHECK_ERROR();

// GPU kernel function: N을 인자로 받아 범위 체크
__global__ void kernel_vec_add(float* C, const float* A, const float* B, const int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {          // boundary check
        C[i] = A[i] + B[i];
    }
}

boundary check if (i < N)는 launch된 스레드 수(dimBlock.x × dimGrid.x ≥ N)와 배열 크기 N이 일치하지 않는 경우를 처리한다. 그래서 커널이 N을 인자로 받는다. 남는 스레드가 배열 밖(인덱스 N 이상)을 읽고 쓰는 것을 막는다.

쉽게 말하면 4인용 테이블에 10명을 앉히려면 테이블 3개(12석)가 필요하다. 남는 두 자리에 앉은 "유령 손님"은 주문하지 못하게 막는 게 if (i < N)다. 교수님 설명대로 grid×block이 항상 N과 정확히 같게(예: N이 1024의 배수) 잡으면 이 검사를 생략할 수 있지만, 혹시 몰라 넣는 것이 일반적이다.
시험 포인트 계산 문제로 잘 나온다. 예를 들어 N = 1025, blockDim = 1024이면 gridDim = (1025 + 1023) / 1024 = 2, 총 스레드는 2048이고 유효 인덱스는 0~1024, 나머지 1023개는 if에서 걸러진다. "(N + B − 1) / B가 왜 올림인가"도 설명할 수 있어야 한다. N이 B의 배수가 아니면 나머지가 B−1 이하로 남아 몫이 정확히 1 증가하기 때문이다.

AXPY와 BLAS

AXPY는 "A X Plus Y", 즉 Z ← aX + Y다. X, Y, Z는 vector이고 a는 scalar다. 선형대수·미분방정식·신경망 학습의 최적화에 자주 나오는 정형화된 연산이다.

  • BLAS(Basic Linear Algebra Subprograms): 선형대수, 행렬/벡터 계산에서 널리 쓰이는 표준 라이브러리다. "Subprogram"은 Fortran 시절 용어로, 역사가 오래되었다는 뜻이다. CUDA 버전은 cuBLAS로 CUDA를 설치하면 함께 깔린다.
  • 자료형별 이름: SAXPY = single precision(float), DAXPY = double precision(double), CAXPY = complex numbers.

FMA 응용: 내적과 LERP

answer ← fma( ax, bx, answer )

lerp(linear interpolation, 선형 보간)는 f(t) = (1 − t)·v₀ + t·v₁이다. t = 0이면 v₀, t = 1이면 v₁, 그 사이에서는 직선 위를 일정한 속도로 움직인다(애니메이션 경로 등에 사용). 그대로 쓰면 곱셈 2 + 덧셈 1이지만, (v₀ − t·v₀) + t·v₁로 바꾸면 FMA 2개가 된다.

float t = 0.5F;   // 0.5면 두 값의 평균
// lerp.cu (일반 식)
Z[i] = (1.0F - t) * X[i] + t * Y[i];
// lerp-fma.cu
Z[i] = fmaf(t, Y[i], fmaf(-t, X[i], X[i]));
함정 안쪽 fmaf(-t, X[i], X[i]) = −t·X + X = (1−t)·X이고, 바깥 fmaf(t, Y[i], 안쪽) = t·Y + (1−t)·X다. 인자 순서는 fma(곱1, 곱2, 더할 값)이다. 또 FMA는 반올림 횟수가 달라 일반 식과 마지막 비트까지 같다고 보장되지 않는다(정밀도가 "약간" 다름). 참고로 슬라이드의 lerp-fma.cu 함수 이름은 axpy 예제 이름(kernel_axpy)이 그대로 남아 있다.

5-1 GPU 스레드와 warp

CUDA 하드웨어 구조: GPC → SM → SP

예시 하드웨어는 NVIDIA Tesla GP100(Pascal)이다. 지금 GPU도 기본 구조는 같고, 개수만 많아졌다.

  • 1 GPU = 6 GPC(graphics processing cluster), 1 GPC = 10 SM → 모두 60 SM
  • SM(streaming multiprocessor) = GPU의 기본 처리 단위(the fundamental processing unit)
  • 최신 구조는 SM 안에 독립 unit이 있다. 1 unit = 32 SP + 16 DP + 8 SFU + 2 Tex
부품역할
SP (streaming processor)FP32 core. CUDA thread 1개를 맡는 scalar ALU
DP (double precision)FP64 core. 속도 때문에 실제로는 float(32비트)를 훨씬 많이 쓴다

G80(GeForce 8 시리즈, 2006)은 unified shader architecture였다. 그래픽스 파이프라인과 CUDA 연산 장치가 섞여 있었다. 지금 구조는 더 단순해졌고 연산 장치 역할이 강조된다.

쉽게 말하면 CUDA 하드웨어가 아무리 발전해도 바뀌지 않은 원칙이 있다. "SM이 있고, 그 안에 core 32개가 한 묶음으로 움직인다." 뒤에 나오는 warp=32의 근거가 바로 이것이다.

Transparent Scalability: 왜 thread block이 필요한가

CUDA 장치는 매우 다양하다. 저가 스마트폰·태블릿은 SM이 1~4개, 일반 PC는 6~200개 정도, high-end 워크스테이션은 1000개 이상이다. 같은 커널 프로그램이 이 모든 장치에서 돌아가야 한다.

  • CUDA의 해결책은 thread block 개념의 도입이다. SM 1개가 thread block 1개를 처리한다.
  • block들을 큐에 넣어 두면 SM이 꺼내 간다. SM이 많을수록 동시에 처리하는 block이 늘어 빨라진다.
  • 각 block은 다른 block과 순서 상관없이(in any order) 실행된다. 처리 속도만 다를 뿐 결과는 같다.
  • 그래서 grid–block–thread 계층 구조가 필요하다.

Thread, warp, lane

thread

독립적 실행의 단위. block 하나에 1~1024개(1D·2D·3D 모양). 모든 thread가 같은 커널 프로그램을 실행하고, block 안에서 thread ID를 가진다.

warp

32 threads 묶음. 물리적으로 (진짜) 동시 실행되는 thread 그룹. warp 안에서 각 thread의 번호가 lane(0~31)이다.

이름은 베틀에서 왔다. 날실(warp threads)은 평행하게 함께 움직이는 여러 가닥이고, 씨실(weft thread)은 그 사이를 꿰는 실 한 줄이다. lane은 수영장·트랙의 1레인, 2레인과 같은 뜻이다.

  • SM이 thread ID를 부여·관리하고, thread 실행을 스케줄링한다.
  • 각 thread block은 32-thread warp로 나뉜다. 이것은 구현상의 결정이지 CUDA 프로그래밍 모델의 일부가 아니다.
  • SM의 CU(control unit) 하나가 core 32개를 관리한다. 그래서 warp의 32 thread는 같은 instruction을 동시에 실행한다.
  • time sharing 관점에서 SM 1개는 2048개 이상의 thread를 동시에 "관리"한다. 메모리의 느린 반응을 이렇게 해결한다.

예제: warp가 몇 개인가?

SM에 block 3개가 배정되고, 각 block은 256 threads라고 하자.

  • block 하나는 256 / 32 = 8 warps, SM 전체는 3 × 8 = 24 warps
  • 그러나 어느 순간이든 24개 중 단 1개의 warp만 선택되어 instruction fetch·실행된다 (core가 32개뿐이므로)
  • warp가 SM의 스케줄링 단위(scheduling unit)이다

Warp 스케줄링: 메모리 지연을 숨기는 time sharing

warp가 선택되면 그 warp의 모든 thread가 같은 instruction을 실행한다. SM에는 control logic이 하나뿐이기 때문이다. 이 방식을 SPMD(single-program, multiple-data) model이라 한다.

문제는 메모리다. read/write instruction을 내면 CUDA 메모리(비디오 메모리)에서 결과가 100+ clock cycle 뒤에 온다. 그동안 core가 놀면 손해다(latency problem). 그래서 scheduling이 필요하다. 운영체제의 time sharing과 같은 발상으로, 목표는 "processor가 쉬지 않게" 하는 것이다.

  • zero-overhead warp scheduling: SM마다 레지스터를 충분히(65,536+ registers) 확보해 두어, 각 warp가 자기 레지스터를 계속 들고 있다. 그래서 warp 전환 때 레지스터를 저장·복원할 필요가 없고, 전환 비용이 (거의) zero-cost다.
  • score-boarding: Instruction Buffer에 있는 모든 instruction의 register operand를 추적한다. 메모리 read/write instruction을 만나면 그 warp는 waiting, instruction의 operand가 모두 준비되면 ready.
  • warp scheduler: 우선순위에 따라 ready 상태의 warp 중 1개를 pick up한다.

Warp Scheduling 예제: warp가 몇 개 있어야 하나

SM = 32 SP, register 명령은 1 clock, 메모리 접근은 100 clock이라 하자. 통계적으로 전형적인 CUDA 프로그램은 명령 4개마다 메모리 접근 1번을 한다. 그러면 100 / 4 = 25 warps가 있어야 core가 쉬지 않는다(good performance).

시험 포인트 "GPU는 메모리 지연을 어떻게 극복하는가?" → SM이 많은 warp를 동시에 관리하며, 메모리를 기다리는 warp는 waiting으로 돌리고 ready warp를 즉시 실행한다(time sharing). 레지스터가 충분해 warp 전환 비용이 거의 0이고(zero-overhead), score-boarding으로 준비 상태를 추적한다. 메모리 지연 자체가 줄어드는 것이 아니라, 그 시간에 다른 일을 해서 숨기는 것이다.

2단계 병렬 처리와 자원 제약

  1. 1단계 (SM 사이): 커널 하나 → grid 하나. grid → thread blocks → 여러 SM에 분산되어 병렬 실행.
  2. 2단계 (SM 내부): 각 SM이 block을 warps로 나누고 score-boarding으로 warp들을 번갈아 병렬 실행.

warp나 block이 끝나면 다음 warp·block을 pick up한다. 단, SM은 칩이라 자원 제약이 있다. 예를 들어 어떤 SM은 thread block을 32개까지, thread는 SM 전체에서 2,048개까지만 받을 수 있다.

warp id, lane id

  • lane id: warp 안에서 자신의 번호(0~31)
  • warp id: SM 안에서 특정 warp의 번호. SM 단위로 관리되어 globally unique가 아니다(다른 SM에 같은 warp id가 있을 수 있음)
  • 둘 다 가져오는 CUDA 함수가 없다. GPU assembly instruction(PTX)으로 확인한다

ROCm(HIP)의 경우

ROCm에서는 warpSize 변수로 계산할 수 있다: lane = threadIdx.x % warpSize, warp = threadIdx.x / warpSize. 단, ROCm의 warpSize는 장치마다 다르다. 서버용 64, 소비자용 32. CUDA는 항상 32로 고정이다.

함정 "warp 크기 32"와 "SM의 core 수"는 다른 개념이다. 또 SM이 24 warp를 관리한다고 24 warp가 동시에 계산되는 것도 아니다. 관리(resident)는 많이, 실행은 한 순간 1 warp(unit당)다.
5-2 행렬 덧셈 (Matrix Addition)

행렬과 행렬 덧셈

  • 행렬 = nrow × ncol 원소의 2D 배열. nrow = 행(row)의 수, ncol = 열(column)의 수
  • 원소 위치는 (row, col), 좌표로 쓰면 (y, x)다. (x, y)가 아니다!
  • C = A + B는 element-by-element 덧셈: cij = aij + bij (행렬 곱셈과 다름)
  • 모든 row, 모든 column에 대해 해야 하므로 2차원 커널이 필요하다
함정 교수님이 여러 번 강조: 행렬 위치는 row, col 순서라 좌표로는 y, x 순서다. 가로가 x(col), 세로가 y(row). 이걸 헷갈리면 5-3의 "잘못된 메모리 설정"이 생긴다.

C/C++의 행렬 저장: row-major

  • logical layout: nrow = height, ncol = width
  • physical layout: C/C++ 2D 배열은 한 행을 통째로 저장하고 다음 행을 잇는다(row-major). M = &(M[0][0]), 원소는 M[y][x]
  • re-interpret: cudaMalloc은 1D 배열을 준다. 같은 메모리를 M[ y * WIDTH + x ]로 읽는다

그래서 2D 배열에서 "각 row, 각 col에 대해 M[row][col]"이던 반복은, 1D 배열에서는 "각 row, 각 col에 대해 index = row * WIDTH + col, M[index]"가 된다.

CUDA 2D Layout과 전역 인덱스

grid·block은 최대 3차원이다. 1D는 1차원 배열, 2D는 행렬·영상, 3D는 3차원 그래픽 자료에 쓴다. grid는 kernel마다 1개이고, grid dimension이 내부 block 배치를, block dimension이 내부 thread 배치를 정한다. block index·thread index는 각각 (x, y, z)다.

예: dim3 gridDim(3,5) → grid 안 2D block index (x, y), dim3 blockDim(4,3) → block 안 2D thread index (x, y). 전체로 펼치면 X 방향 3 blocks·12 threads, Y 방향 5 blocks·15 threads다.

__global__ void kernel( float* A, int WIDTH, int HEIGHT ) {
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int i = gy * WIDTH + gx;
    ...
}

blockIdx, threadIdx의 조합은 thread마다 unique하다. (gx, gy)가 global 2D index이고, 행렬에서는 gy가 row, gx가 col이다. 커널에서 쓸 것은 threadIdx의 x, y가 아니라 전역 x, y다.

Thread block 설계: 32 × 32, 그리고 남는 thread

  • 10,000 × 10,000 행렬에는 32 × 32 thread block(= 1,024 threads)을 선호한다. block 하나의 최대 thread 수가 1024 = 32 × 32라 꽉 찬다.
  • 10,000 / 32 = 312.5 → grid size = 313 × 313
  • 32 × 313 = 10,016 → total threads = 10,016 × 10,016. 오른쪽 16열·아래 16행의 thread는 아무 일도 하지 않는다(do nothing threads)
dim3 dimBlock(32, 32, 1);
dim3 dimGrid((ncol + dimBlock.x - 1) / dimBlock.x, (nrow + dimBlock.y - 1) / dimBlock.y, 1);
함정 grid의 x는 열 수(ncol), y는 행 수(nrow)로 계산한다. 정방 행렬이면 값이 같아 티가 안 나지만 직사각 행렬이면 틀린다.

5-3 2차원 메모리 할당 (pitch)

DRAM 구조와 bursting

  • DRAM(Dynamic RAM): capacitor(축전기) 구조로 1 bit를 저장한다. 느리고 휘발성이지만 값싸다(cost-effective).
  • capacitor를 2D layout으로 조밀하게 배치한다(보통 1M개 → 1 bit 출력). 주소의 high address로 row를 선택하면 그 row 전체가 MUX로 이동하고, low address로 column을 선택해 1 bit를 내보낸다.
  • 칩을 8/16/32개 병렬로 연결해 같은 주소를 주면 8/16/32 bit DRAM 모듈이 된다.

DRAM bursting: 특정 번지를 access하면 row 하나 전체를 이미 가져와 있다. 그래서 바로 다음 번지를 요청하면 다시 읽을 필요 없이 이미 가져온 것을 그대로 준다. 대부분의 메모리 접근은 sequential이고(아니면 이웃 결과는 버림), 현대 DRAM은 항상 burst mode로 접근하도록 설계된다.

메모리 대응 관계와 "잘못된 메모리 설정"

올바른 커널에서는 warp 하나(x 방향으로 이웃한 32 thread)가 index = y * WIDTH + x로 접근하므로, cudaMalloc한 1D 메모리에서 연속된 32개 주소를 읽는다 → burst 한 번. 오른쪽 끝에 걸린 warp는 16개만 연속 접근하고 16개는 버린다.

x와 y를 뒤바꾸면(index = x * WIDTH + y) 이웃한 32 thread가 행마다 하나씩, 즉 WIDTH 간격으로 흩어진 주소를 건드린다 → 메모리 접근 32번(끝 warp는 16번)으로 쪼개진다.

// mat-add-col-major.cu : 잘못된 설정
int row = blockIdx.x * blockDim.x + threadIdx.x;  // gx  ← 틀림
int col = blockIdx.y * blockDim.y + threadIdx.y;  // gy  ← 틀림
if (row < NROW && col < NCOL) { int i = row * NCOL + col; C[i] = A[i] + B[i]; }

// correct way:
int row = blockIdx.y * blockDim.y + threadIdx.y;  // gy
int col = blockIdx.x * blockDim.x + threadIdx.x;  // gx

Memory Coalescing (메모리 합병)

memory coalescing = 메모리 효율을 높이는 방법이다. 이웃 thread들의 접근을 하나의 큰 전송으로 합친다.

  • DRAM은 chunk(덩어리) 단위로 읽힌다. word 하나만 읽어도 chunk 전체를 읽으며, 다 쓰지 않으면 bandwidth가 낭비된다.
  • chunk는 32/64/128 bytes의 배수에 정렬되어 있다. 정렬되지 않은(unaligned) 접근은 비용이 더 든다.
  • warp마다 128 byte chunk 전송: 32 threads × 4 bytes(float/int) = 128 bytes
  • CUDA의 해결책: cudaMalloc()은 메모리를 최소 256 byte boundary에 정렬한다. 최신 architecture는 4K byte 이상의 boundary를 쓴다.

C++에서는 alignas( integer )로 alignment boundary(byte 수)를 지정하고, alignof( variable )로 alignment 값을 얻는다.

cudaMallocPitch: 2차원 배열을 위한 malloc

cudaMalloc으로 10,000 × 10,000 float를 잡으면 첫 행은 정렬되지만, 두 번째 행은 40,000 byte 뒤에서 시작한다. 40,000은 256의 배수가 아니므로 행 시작이 boundary에서 어긋난다. 해결책은 각 행 끝에 padding을 붙여 모든 행의 시작을 boundary에 맞추는 것이다.

새로운 구현: 더 큰 행렬(oversized)로 경계 검사 없애기

아이디어: thread는 10,016 × 10,016개가 돈다. 메모리를 그보다 넉넉하게 잡아 두면, 바깥쪽 "do nothing" thread도 할당된 메모리 안을 건드린다. 그 영역은 어차피 버리는 값이니 쓰레기를 계산해도 상관없다. 그러면 모든 thread에서 memory 오류가 없고, 커널에서 if 문 검사를 뺄 수 있다.

  • 가로: pitch(원소 단위 stride)가 launch된 x thread 수(10,016) 이상이어야 한다.
  • 세로: 행 수를 NROW가 아니라 numThread.y(launch된 y thread 수)만큼 잡는다.
// mat-add-pitched.cu : 두 커널 모두 NCOL 대신 stride로 행을 건너뜀
__global__ void kernel_mat_add(float* C, const float* A, const float* B,
                               int NROW, int NCOL, size_t stride) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;  // gx
    int row = blockIdx.y * blockDim.y + threadIdx.y;  // gy

3D 데이터와 filtering

컴퓨터는 이미지를 행렬(matrix)로 저장·해석한다. 640×480 이미지는 픽셀(단위 정사각형) 640×480개이고, 각 픽셀 값은 0.0(black)~1.0(white) 또는 0(black)~255(white)이다. 이것이 image processing(영상 처리)의 수학적 배경이다.

CT(computed tomography, 컴퓨터 단층 촬영)는 X-ray를 여러 장 차례로 찍는다. X-ray 1장은 2D 행렬이고, 여러 장을 쌓으면 3D 행렬 집합(matrix set)이 된다. 그래서 3D 데이터 처리는 곧 행렬 계산이다.

이 강의의 image filtering은 (given image) × (filter image) → (new image)이고, 행렬 연산으로는 element-by-element multiplication이다. 즉 C[i] = A[i] * B[i]로 같은 위치끼리만 곱한다.

함정 여기서 말하는 filtering은 이웃 픽셀을 합하는 convolution이나 행렬 곱셈이 아니다. 같은 위치의 원소끼리 곱할 뿐이라 thread끼리 데이터를 주고받을 일이 없다.

3D 배열의 1D 저장 (row-major)

C/C++의 3D 배열 M[z][y][x]는 크기가 depth × height × width이고, 메모리에서는 결국 1D array로 놓인다. depth = 0 한 장(slice)이 행 단위로 통째로 먼저 놓이고, 그 뒤에 depth = 1이 이어진다. x가 가장 빨리 변한다.

그래서 1D 인덱스는 i = (z * HEIGHT + y) * WIDTH + x이다. 앞에 있는 slice z장(z × HEIGHT행)과 같은 slice 안의 y행을 건너뛴 뒤 x칸 더 가는 것이다.

예제 3d-filter.cu는 300 × 300 × 256 데이터를 쓴다. dim3에는 x, y, z 순서(width, height, depth)로 담고, CPU는 z → y → x 삼중 반복을 한다. host 쪽 pitch는 압축(packed compactly)이므로 300 * sizeof(float) = 1200 byte다.

CUDA naïve 구현: 3D launch와 버려지는 thread

1D·2D에서는 block당 최대 1024 thread를 썼지만, 1024는 x, y, z 세 축에 고르게 나누기 어렵다. 그래서 3D 응용에서는 정육면체 모양인 8 × 8 × 8 = 512 threads/block을 선호한다(꼭 그래야 하는 것은 아니다).

  • grid = ⌈300/8⌉ × ⌈300/8⌉ × ⌈256/8⌉ = 38 × 38 × 32 blocks
  • 전체 thread = 304 × 304 × 256. x, y축 끝에서 4개씩(38 × 8 = 304 − 300) 남는 thread는 아무것도 하지 않는다(do nothing threads).
  • 나머지 action thread들이 연속된 memory 영역에 index = (z * HEIGHT + y) * WIDTH + x로 대응된다.

device 쪽도 cudaMalloc으로 compact하게 잡고(device pitch도 1200 byte), 커널은 세 축의 전역 좌표를 구한 뒤 세 축 모두 경계를 검사한다.

cudaPitchedPtr: pitch를 품은 포인터

3D가 되면 주소 계산에 실제 포인터, pitch, x 폭, y 높이를 모두 알아야 한다. 이것을 하나로 묶은 구조체가 cudaPitchedPtr이다. 커널에 포인터와 pitch를 따로 넘기지 않고 이 구조체 하나로 넘긴다.

6-2 CUDA 메모리 계층구조

왜 메모리 계층인가

register와 memory는 서로 보완 관계다. Registers are very fast: instruction당 1 clock tick, 메모리 접근이 없다. 대신 비싸서 양이 적다(thread당 대략 1K개 수준). Memory is slow, but very large scale: CPU/GPU당 16GB 이상이지만 read/write 한 번에 100+ clocks가 든다. CPU는 그 사이를 cache로 메운다.

CUDA의 메모리 5종 (Programmer's View)

CUDA는 같은 구조를 더 잘게 나눈다. 하나의 thread block은 하나의 SM(streaming multiprocessor)에서 실행되고, 각 thread는 다음을 할 수 있다.

Race condition과 __syncthreads()

전형적인 시나리오: 모든 thread가 shared의 한 칸에 쓰고(shared[i] = value; — every thread does it), 나중에 모든 thread가 다른 thread가 쓴 칸을 읽는다(another = shared[j]; — every thread needs it).

문제는 thread가 warp 단위로 실행되고 warp마다 실행 속도가 다를 수 있다는 점이다. 빠른 warp가 shared[j]를 쓰려고 도착했는데, 그 값을 써 줘야 할 느린 warp는 아직 update 전일 수 있다. 그러면 잘못된 값을 읽어 결과가 틀린다. 이것이 race condition이다.

Barrier Synchronization

  • CUDA intrinsic function(내장 함수): 컴파일러가 해당 위치에 특별한 code(명령어)를 직접 생성한다. 함수 call이 일어나지 않는다(C++ inline과 비슷). 그중 하나가 __syncthreads().
  • 정의: All threads in the same thread-block must reach the __syncthreads() before any thread can move on.
  • 목적: 모든 원소가 updated(write)되었음을, 그리고 모든 원소가 consumed(read)되었음을 보장.
  • 주의: heavy operation. 필요할 때만 쓸 것.
__global__ void kernel_func(void) {
    __shared__ float shared[SIZE];
    ...
    shared[i] = value;
    __syncthreads();        // we can assume it is done !
    ...
    another = shared[j];    // every threads need it
}
함정 __syncthreads()의 범위는 같은 block뿐이다. 다른 block과는 동기화되지 않는다. host에서 부르는 cudaDeviceSynchronize()(커널 전체 완료를 기다림)와는 호출 위치와 범위가 다르다. 또 소스에서 쓰기 문장이 위에 있다고 다른 thread가 이미 거기까지 실행했다는 보장은 없다.

Adjacent difference 문제

각 원소에 대해 인접한 원소 사이의 차이를 구한다: vecB[i] = vecA[i] − vecA[i − 1]. exceptional case는 i = 0으로, 존재하지 않는 vecA[−1] 자리에 0을 써서 vecB[0] = vecA[0] − 0.0f이다. CUDA 설계는 i번째 thread가 vecB[i] 하나를 맡는다(모두 n개의 thread).

int N = 1024 * 1024 * 1024; // 1G elements

__host__ void kernel_cpu_adj_diff(int i, float* B, const float* A) {
    if (i == 0) { B[i] = A[i] - 0.0F; }
    else        { B[i] = A[i] - A[i-1]; }
}

__global__ void kernel_adj_diff(float* B, const float* A, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i == 0) {
        B[i] = A[i] - 0.0f;
    } else if (i < N) {
        B[i] = A[i] - A[i - 1];   // two global memory read: A[i], A[i-1]
    }                              // one global memory write: B[i]
}

시험 포인트 실행 결과 읽기: B[0] = A[0] = 0.823(0을 뺐으니 그대로), B[1] = 0.828 − 0.823 = 0.005, B[2] = 0.755 − 0.828 = −0.073. "B의 첫 값은 0이다"라고 쓰면 틀린다. 또 naïve 커널에서 이웃 thread의 A[i]가 내 A[i−1]이라 같은 원소를 global에서 두 번 읽는다. 이 중복이 shared 버전의 동기다.

Shared memory 구현 (adj-diff-shared.cu)

각 thread가 자기 원소 A[i]를 shared buffer의 자기 자리 s_Buf[tx]에 올리고, __syncthreads()로 모두 올라올 때까지 기다린 뒤, 이웃 값은 s_Buf[tx-1]에서 읽는다. 단 block의 첫 thread(threadIdx.x = 0)는 바로 앞 원소가 자기 tile 밖(앞 block 담당)에 있으므로 vecB[i] = s_Buf[tx] − vecA[i−1]로 global에서 직접 읽는다.

Tiled approach (1D)

tile = 하나의 thread block을 위한 shared memory 조각이다. 전체 global 데이터를 block 단위로 자르고, 한 block이 자기 몫을 shared로 가져온 덩어리가 tile이다. 같은 원소를 두 가지 인덱스로 부른다.

  • global index = blockIdx.x * blockDim.x + threadIdx.x → global memory에서의 위치
  • block number = blockIdx.x → 몇 번째 tile인가
  • local index = threadIdx.x → tile(shared) 안에서의 위치
__global__ void kernel_adj_diff(float* B, const float* A, int N) {
    __shared__ float s_Buf[1024];    // shared memory buffer (= blockDim.x)
    int i = blockIdx.x * blockDim.x + threadIdx.x;  // global index
    int tx = threadIdx.x;                            // local index
    if (i < N) {
        s_Buf[tx] = A[i];
        __syncthreads();
        if (i == 0) {
            B[0] = s_Buf[0] - 0.0F;           // 배열 전체의 첫 원소
        } else if (tx == 0) {
            B[i] = s_Buf[tx] - A[i - 1];      // block 경계: 앞 원소는 global에서
        } else {
            B[i] = s_Buf[tx] - s_Buf[tx - 1];
        }
    }
}
// one global memory read:  A[i]
// two shared memory read:  s_Buf[tx], s_Buf[tx-1]
// one global memory write: B[i]
  • tx: threadIdx.x를 매번 쓰기 길어서 레지스터 변수에 담는 CUDA 프로그래머들의 흔한 테크닉. 속도 차이는 없다.
  • block의 1024 thread가 동시에 한 개씩 복사하므로, __syncthreads() 직후에는 global의 1024개가 한 스텝에 tile로 들어와 있다.
  • 예외가 두 종류다: 배열 전체의 첫 원소(i == 0, 0을 뺌)와 각 block의 첫 thread(tx == 0, global에서 A[i−1]).

시험 포인트 서술형 "shared 버전이 유리한 이유와 __syncthreads()가 필요한 이유": 이웃 thread가 같은 A 원소를 각각 global에서 읽던 것을, block이 한 번씩만 읽어 shared에 두고 재사용하므로 global read가 2회 → 1회로 준다. 그런데 s_Buf[tx−1]은 다른 thread가 쓴 값이므로, 쓰기가 끝나기 전에 읽지 않도록 load와 사용 사이에 barrier가 반드시 있어야 한다.

7-1 유연한 shared memory (Flexible Shared Memory)

6주차에 shared memory와 race condition, adjacent difference를 배웠다. 이번 강의는 그 shared memory를 더 잘 쓰는 요령 다섯 가지다. barrier를 최소한으로 쓰기, shared 배열 크기를 실행 중에 정하기, 프로그램 안에서 device 정보 묻기, deviceQuery 유틸리티, 커널 안 포인터 주의점.

barrier는 필요한 만큼만: adj-diff-overuse

__syncthreads()는 block 안 모든 thread가 그 지점에 올 때까지 멈추게 하는 barrier다. 데이터가 준비됐음을 보장하려고 쓰지만 슬라이드 표현 그대로 heavy operation이라 필요할 때만 쓴다.

adj-diff-overuse.cu는 6-3의 shared 버전에 barrier를 하나 더 넣었다. 결과 B[i]를 다 쓴 뒤에 "한 번 더 맞춰 두면 나쁠 것 없겠지" 하고 넣은 것이다. 슬라이드의 답은 "속도 저하를 가져옴. 하지 말 것!"

__global__ void kernel_adj_diff(float* B, const float* A, int N) {
    __shared__ float s_Buf[1024];          // shared memory buffer
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int tx = threadIdx.x;
    if (i < N) {
        s_Buf[tx] = A[i];
        __syncthreads();                   // ① 필수: 이웃(tx-1)의 값이 들어왔음을 보장
        if (tx > 0)      B[i] = s_Buf[tx] - s_Buf[tx - 1];
        else if (i > 0)  B[i] = s_Buf[tx] - A[i - 1];
        else             B[i] = s_Buf[i] - 0.0F;   // i == 0
        __syncthreads();                   // ② overuse: 이후 이 데이터를 읽는 thread가 없다
    }
}

①은 다른 thread가 쓴 s_Buf[tx-1]을 읽기 전에 꼭 있어야 한다. ②는 그 뒤에 shared 데이터를 읽는 코드가 없으니 아무것도 보장하지 않고, block 전체를 한 번 더 세워 놓기만 한다.

CUDA에서는 overuse가 shared 버전보다 느려졌다(6.455 → 6.675 ms). ROCm에서는 차이가 거의 없다. 교수님은 이를 "하드웨어에 따라 barrier 부담이 다르다"고 해석하면서, 직접 여러 버전을 재 보고 고르는 게 가장 좋지만 어렵다면 CUDA 권고를 따르라고 했다. 권고는 두 줄이다. shared memory는 웬만하면 쓰고, __syncthreads()는 overuse하지 마라.

시험 포인트 "barrier를 많이 넣으면 더 안전하지 않은가?"에는 이렇게 답한다. barrier는 다른 thread가 쓴 shared 데이터를 읽기 전에만 의미가 있다. 그 밖의 barrier는 block의 모든 thread를 가장 느린 thread에 맞춰 기다리게 하는 비용일 뿐이다. 필요한 barrier를 빼라는 뜻은 아니다. 빼면 race condition이 생긴다.

flexible size shared memory: extern과 launch의 세 번째 인자

shared 배열의 크기는 보통 __shared__ float s_Buf[1024];처럼 컴파일 때 고정한다. 그런데 필요한 크기는 block 크기에 따라 달라진다(thread당 원소 1개면 blockDim.x개). block 크기를 실행 중에, 기계마다 다르게 정한다면 shared 크기도 그때 정해야 한다.

  • 커널: extern __shared__ float s_Buf[]; 크기를 비워 두므로 "배열이라는 사실"만 안다.
  • launch: kernel<<< dimGrid, dimBlock, sizeInByte >>>(...) 세 번째 인자가 thread block마다 할당할 shared memory의 byte 수다.
  • launch 때 malloc하듯 잡으므로(dynamic allocate) 약간 느려질 수 있다.
__global__ void kernel_adj_diff(float* B, const float* A, int N) {
    extern __shared__ float s_Buf[];       // size not fixed at compile time
    ...                                    // 본문은 같음, 뒤쪽 barrier는 제거
}
int main(...) {
    dim3 dimBlock(512, 1, 1);              // 일부러 1024 → 512
    dim3 dimGrid((N + dimBlock.x - 1) / dimBlock.x, 1, 1);
    int bufSizeInByte = dimBlock.x * sizeof(float);    // 512 * 4 = 2048
    kernel_adj_diff<<< dimGrid, dimBlock, bufSizeInByte >>>(devPtrB, devPtrA, N);
    ...
}

결과는 의외로 global 버전(5.818 ms)보다도 빨랐다. 교수님 해석은 "설정(block 크기)에 따라 shared 버전이 빨라지는 지점을 찾을 수도 있다"이다. 이 예제의 진짜 의의는 shared 크기를 block 크기에 맞춰 조정할 수 있다는 데 있다. ROCm에서는 의미 있는 차이가 없었다.

함정 세 번째 인자는 byte 단위이고 block 하나당 크기다. 원소 개수(512)도 아니고 grid 전체 크기(N×4)도 아니다. block 크기를 바꾸면 이 값도 같이 바꿔야 한다. 또 1024 고정판과 비교할 때 block 크기(1024→512)도 함께 바뀌었으므로, 빨라진 이유를 extern 문법 하나로 돌리면 안 된다.

커널 안의 pointer 변수

커널 안에서 포인터를 쓸 수 있고, global·constant·shared 어느 공간이든 가리킬 수 있다.

__device__   int my_global_variable;
__constant__ int my_constant_variable = 13;
__global__ void foo(void) {
    __shared__ int my_shared_variable;
    int*       ptr_to_global   = &my_global_variable;
    const int* ptr_to_constant = &my_constant_variable;
    int*       ptr_to_shared   = &my_shared_variable;
    ...
    *ptr_to_global = *ptr_to_shared;      // shared 값을 global로
}

핵심 문장: Pointers are NOT typed on memory space. __shared__ int* ptr;에서 __shared__는 ptr 변수 자체가 shared memory에 산다는 뜻이다. "shared 변수를 가리키는 포인터"가 아니다. 그 안에 담는 주소는 global이든 constant든 상관없다. 아무 수식어 없이 커널 안에서 선언한 포인터는 register에 놓인다.

__device__ int my_global_variable;
__global__ void foo(int* input) {
    __shared__ int my_shared_variable;
    int* ptr = nullptr;
    if (input[threadIdx.x] % 2) ptr = &my_global_variable;
    else                        ptr = &my_shared_variable;
    // where does ptr point?  → thread마다 다름
}

같은 warp 안에서 같은 포인터 코드가 어떤 thread는 global, 어떤 thread는 shared를 가리키면 옛 CUDA는 system crash가 났고, 지금은 crash 대신 성능 저하가 생긴다(전체가 global 접근처럼 느려진다). 그래서 CUDA 권고는 다음과 같다.

  • 포인터는 simple, regular access pattern으로만 역참조한다.
  • pointer to pointer는 피한다. GPU는 pointer chasing을 싫어한다. linked list·tree는 잘 동작하지 않는다(그래서 CUDA 예제는 거의 배열만 쓴다).
  • 컴파일러 경고 Cannot tell what pointer points to, assuming global memory space를 무시하지 않는다. 나중에 crash로 이어질 수 있다.

kernel 인자의 memory space

  • kernel 호출은 기본적으로 call-by-value다. struct를 넘기면 struct가 통째로 복사된다(예: pitched pointer 구조체). 그 안의 포인터가 가리키는 큰 배열까지 복사되는 것은 아니다.
  • 포인터 인자는 모두 CUDA global memory에 있다고 가정한다. int dim[3] 같은 배열을 넘기면 커널은 int* dim으로 받고 global memory에서 찾는다.
  • 흔한 실수: dim이 host 메모리에 있는 경우. 옛 CUDA는 바로 에러가 났고, 요즘은 managed memory 등으로 동작하기도 하지만 느려진다. 늘 device에 할당한 주소를 넘기는 것이 정석이다.
쉽게 말하면 __shared__ 같은 수식어는 "그 변수가 어느 방에 사는가"를 말한다. 포인터 변수가 shared 방에 살아도, 쪽지에 적힌 주소는 global 방일 수 있다. 그리고 커널이 받는 주소는 기본적으로 "global 방 주소"로 읽힌다.
7-2 행렬 복사 (Matrix Copy)와 2D tile

왜 하필 행렬 복사인가: 이론적 한계

할 일은 C[i,j] = A[i,j] 하나다. 성능을 위해 pitched matrix를 쓰고, 단순하게 square matrix(N×N)를 가정한다. 이렇게 단순한 연산에 한 강의를 쓰는 이유는 이것이 모든 행렬 연산의 theoretical limit(이론적 한계), 곧 best score(최고 기록)이기 때문이다.

  • 어떤 행렬 연산도 "원소마다 한 번 읽고 한 번 쓰기"보다 적게 일할 수 없다. 그러니 복사보다 빠를 수 없다.
  • 최적화한 연산이 이 기록에 가까워질수록 잘 최적화된 것이다.
  • 이 기록을 추월했다면 뭔가 잘못됐다. 계산을 빠뜨렸거나 잘못 구현한 것이다.
  • 속도보다 먼저 결과가 맞는지 확인한다. "답은 똑바로, 속도는 복사에 근접"이 목표다.

CPU 판과 CUDA global 판

CPU 판은 이중 for문으로 kernel_cpu_mat_copy(r, c, matC, matA)를 N×N번 부르고, 안에서 i = y * N + x; C[i] = A[i];를 한다. CUDA 판은 thread 하나가 원소 하나를 맡아 같은 global index (gy, gx) 자리로 옮긴다. 강의는 좌표를 항상 (y, x) 순서로 쓴다는 점을 주의하라고 했다.

pitched 행렬에서 A[y][x]의 위치는 두 가지로 계산할 수 있다. dev_pitch는 cudaMallocPitch(), cudaMalloc3D()가 돌려주는 byte 단위 값이다. 요즘 CUDA의 pitch는 256·512의 배수처럼 커서 sizeof(float)=4의 배수이기도 하므로, 강의 커널은 원소 단위 stride로 계산한다.

// GPU kernel function
__global__ void kernel_mat_copy(float* C, const float* A, int N, size_t stride) {
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    if (gy < N && gx < N) {
        int i = gy * stride + gx;
        C[i] = A[i];
    }
}
// GPU kernel function for oversized matrices: if 검사 없음
__global__ void kernel_mat_copy_oversize(float* C, const float* A, size_t stride) {
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    int i = gy * stride + gx;
    C[i] = A[i];
}
// main: int stride = devPitchA / sizeof(float);
//       if (numThread.x <= devPitchA) → oversize 커널, else → 일반 커널

oversize 커널은 5주차에서 본 기법이다. 할당을 thread 수만큼 넉넉하게 잡아 두면, 범위 밖 thread가 쓰레기 값끼리 복사해도 문제가 없으니 if를 뺀다. 요즘 CUDA에서는 device pitch가 thread 수보다 크거나 같아 이 분기로 들어간다.

host pitch = 40000 (byte), host stride = 10000 (element) CPU kernel: elapsed time = 61.928 msec prob size = 10000 * 10000 gridDim = 313 * 313 * 1 blockDim = 32 * 32 * 1 total thr = 10016 * 10016 * 1 device pitch = 40448 (byte), device stride = 10112 (element) oversized case = true GPU kernel: elapsed time = 0.616 msec

읽는 법: host는 compact라 pitch = 10000×4 = 40000. device는 정렬 때문에 40448 byte로 늘고 stride는 10112. grid는 ⌈10000/32⌉ = 313, 전체 thread는 313×32 = 10016. 이 0.616 ms(ROCm 6.038 ms)가 global memory에서 행렬을 복사하는 최소 시간, 곧 이후 모든 행렬 연산의 기준선이다.

2D tiled layout: global index와 local index

CUDA에서 tile이라는 말이 나오면 "shared memory를 쓰겠다"로 이해하면 대체로 맞다. 행렬을 block 단위로 잘라 block 하나를 shared memory의 작은 2D 배열(tile)에 올린다.

이름식의미
block number(blockIdx.x, blockIdx.y)grid = block들의 2D 배치에서 몇 번째 block인가
global indexgx = blockIdx.x*blockDim.x + threadIdx.x

서로 다른 block의 thread도 local index (ty, tx)는 같을 수 있다. global 위치는 다르다. 복사할 때 global (gy, gx)의 값이 local (ty, tx) 칸으로 간다.

tile 크기: 32 × 32

tile은 정사각형을 선호한다(편하고 벤치마크에서도 빠르다). 크기는 거의 고민 없이 __shared__ float s_mat[32][32];를 쓴다.

  • 32 × 32 = 1,024 = 한 thread block의 최대 thread 수 → thread 하나가 tile 칸 하나
  • 32 = a single warp → tile의 한 행이 warp 하나
  • tile 메모리: 1024 × 4 B = 4096 B
  • 옛 코드의 16×16(=256)이나 32×16(=512, thread 하나가 2개씩 처리해 32×32로 작동)은 block 최대 thread가 512이던 시절의 흔적이다. 지금은 쓰지 않는 deprecated 방식이다.

shared tile로 복사: mat-copy-shared

__global__ void kernel_mat_copy_oversize(float* C, const float* A, size_t stride) {
    __shared__ float s_mat[32][32];
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    int ty = threadIdx.y;
    int tx = threadIdx.x;
    int i = gy * stride + gx;
    s_mat[ty][tx] = A[i];      // global → shared
    __syncthreads();
    C[i] = s_mat[ty][tx];      // shared → global
}

결과는 0.641 ms로 global 판(0.616 ms)보다 약간 느렸다. shared를 한 번 더 거치고 barrier도 있으니 정상이다. 엄밀히는 각 thread가 자기가 쓴 칸만 다시 읽으므로 이 복사에서는 barrier가 없어도 된다. 그래도 뒤의 연산들과 비교하려고 넣어 두는 것이 안전하다고 했다. ROCm은 6.038 vs 6.037 ms로 오차 범위 안이다. 이 예제의 목적은 속도가 아니라 "tile에 가져와서 처리하고 내보내는 골격"을 확보하는 것이다. 바로 다음 전치에서 이 골격을 쓴다.

memcpy()와 cudaMemcpy2D()

행렬이 메모리에 row-major로 길게 놓여 있으니, 그냥 연속 메모리를 통째로 복사해도 된다.

  • void* memcpy(void* destination, const void* source, size_t num); main memory에서 source → destination으로 num byte를 복사한다. 두 영역이 겹치면 실패할 수 있다(memmove() 참고).
  • cudaMemcpy(dst, src, nbytes, direction): 이전 CUDA 호출이 모두 끝나야 시작하고, 복사 중 CPU thread도 멈춘다. direction은 HostToDevice / DeviceToHost / DeviceToDevice / HostToHost.
  • cudaMemcpy2D(dst, dpitch, src, spitch, width, height, kind): pitched 할당끼리 복사한다. dpitch·spitch·width는 byte, height는 행(원소) 수다.
memcpy(matC, matA, N * N * sizeof(float));                              // CPU
cudaMemcpy2D(devMatC, devPitchC, devMatA, devPitchA, N * sizeof(float), N,
             cudaMemcpyDeviceToDevice);                                 // GPU
cudaDeviceSynchronize();

7-3 행렬 전치 (Matrix Transpose)

전치 연산과 CPU 판

C = AT, 즉 ci,j = aj,i. 주대각선을 기준으로 행과 열을 뒤집는다. 역시 square matrix를 가정하고, 입력 A와 출력 C는 서로 다른 배열이다(제자리 전치가 아니다).

__host__ void kernel_cpu_mat_transpose(int y, int x, float* C, const float* A) {
    int indA = y * N + x;
    int indC = x * N + y;     // 읽는 index와 쓰는 index가 다르다
    C[indC] = A[indA];
}

naive CUDA 판: 읽기는 연속, 쓰기는 흩어짐

입력은 global index (gy, gx)에서 읽고, 출력은 x and y swapped, 즉 (gx, gy) 자리에 쓴다.

__global__ void kernel_mat_transpose(float* C, const float* A, int N, size_t stride) {
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    if (gy < N && gx < N) {
        int indA = gy * stride + gx;
        int indC = gx * stride + gy;
        C[indC] = A[indA];
    }
}   // oversize 판은 if만 뺀 것

결과는 CUDA 1.084 ms로 복사(0.616 ms)의 약 2배다. 원인은 계산이 아니라 메모리 접근 패턴이다. 한 warp는 threadIdx.x가 연속인 32 thread다. 이들이 읽는 indA는 1씩 늘어 연속 주소라 한 번에 묶어 처리된다. 이것을 coalesced access라 한다. 반면 쓰는 indC는 stride(10112)씩 떨어져 32개의 따로 떨어진 쓰기가 된다. DRAM은 옆으로 쭉 읽고 옆으로 쭉 쓸 때 효율이 좋다.

ROCm은 6.038 → 8.582 ms로 덜 느려졌다. 이렇게 시간을 재는 이유는 새 연산이 "합리적으로" 구현됐는지 확인하기 위해서다. 복사보다 빠르면 잘못이고, 터무니없이 느려도 문제다.

shared 1차 시도: transpose-shared

tile 골격을 그대로 써서 A의 tile을 s_mat[ty][tx]로 가져오고("got (x,y)"), 출력은 여전히 x·y를 바꾼 global index로 보낸다("move (y,x)").

__global__ void kernel_mat_transpose(float* C, const float* A, int N, size_t stride) {
    __shared__ float s_mat[32][32];
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    if (gy < N && gx < N) {
        int ty = threadIdx.y;
        int tx = threadIdx.x;
        int indA = gy * stride + gx;
        int indC = gx * stride + gy;       // 출력 index는 naive와 같다
        s_mat[ty][tx] = A[indA];
        __syncthreads();
        C[indC] = s_mat[ty][tx];           // 자기가 가져온 값을 자기가 쓴다
    }
}

결과 1.133 ms로 오히려 조금 느려졌다(ROCm 8.472 ms, 오차 범위). indC가 그대로이므로 global 쓰기가 여전히 흩어진다. shared를 한 번 거쳐 가는 비용만 늘었다. shared를 쓰는 것만으로는 빨라지지 않는다.

tiled approach 개선: transpose-block (block swapped)

발상: tile이 이미 shared에 있으니 block 안 thread 누구든 어떤 칸이든 읽을 수 있다. 그런데 "내가 가져온 값을 꼭 내가 써야 하나?" 꼭 그럴 필요가 없다. 그래서 전치를 두 단계로 나눈다.

  1. block 위치만 교환: 출력 block은 (blockIdx.x, blockIdx.y)를 바꾼 대칭 자리. 하지만 block 안의 thread 위치(threadIdx.x는 가로)는 그대로 → 출력도 행 방향으로 쓴다.
  2. tile 안에서 전치: shared에서 s_mat[tx][ty], 즉 대칭 위치의 값을 읽는다.
__global__ void kernel_mat_transpose(float* C, const float* A, int N, size_t stride) {
    __shared__ float s_mat[32][32];
    int gy = blockIdx.y * blockDim.y + threadIdx.y;
    int gx = blockIdx.x * blockDim.x + threadIdx.x;
    if (gy < N && gx < N) {
        int ty = threadIdx.y;
        int tx = threadIdx.x;
        int indA = gy * stride + gx;
        s_mat[ty][tx] = A[indA];                       // 행 방향으로 읽어 행으로 저장
        __syncthreads();
        gy = blockIdx.x * blockDim.x + threadIdx.y;    // same block, different position
        gx = blockIdx.y * blockDim.y + threadIdx.x;
        int indC = gy * stride + gx;                   // threadIdx.x → 연속 주소
        C[indC] = s_mat[tx][ty];                       // tile 안에서 전치
    }
}

확인: block (bx, by)의 thread (tx, ty)는 A[by·32+ty][bx·32+tx]를 s_mat[ty][tx]에 넣었다. 그리고 C[bx·32+ty][by·32+tx] = s_mat[tx][ty] = A[by·32+tx][bx·32+ty]를 쓴다. 행·열이 정확히 뒤바뀌었으니 전치가 맞다.

결과 0.796 ms(ROCm 6.689 ms). global 읽기와 쓰기가 모두 행 방향 연속 접근이 되어 확실히 빨라졌다. ROCm은 이 단계에서 이미 shared 복사(6.037 ms)와 비슷해졌다.

시험 포인트 서술 핵심은 "shared라서 빠르다"가 아니다. shared tile이 block 내부의 재배치 장소가 되어 global 읽기와 쓰기 양쪽을 coalesced로 만든다가 답이다. 전치를 block 단위(위치 교환)와 tile 단위([tx][ty] 읽기)로 나눠 맡긴다. 둘 중 하나만 바꾸면 전치가 완성되지 않는다.

shared memory의 bank 구조

CUDA는 더 빨라질 수 있다(0.796 vs 복사 0.641 ms). 남은 원인은 shared memory 자체의 구조다. shared memory는 DRAM과 다른 SPRAM(scratch-pad RAM)이고, banked 구조다. 현재 CUDA는 32개 bank로 나뉜다. warp 하나가 32 thread이므로, thread마다 bank 하나씩 쓰라는 설계다. bank마다 별도의 데이터 버스가 있어서 32 thread가 서로 다른 bank를 쓰면 순서가 뒤섞여 있어도 한 사이클에 끝난다.

warp의 접근예결과
best casethread k가 a[k]bank 0~31에 하나씩 → 32 thread가 a single cycle
broadcast case모든 thread가 a[0]bank 0이 같은 값 하나를 모두에게 broadcast → a single cycle
2-way conflicta[2*tx]thread k와 k+16이 같은 bank → 2번에 나눠 처리
16-way conflicta[16*tx]짝수 thread는 모두 bank 0, 홀수는 bank 16 → 16번
serialized case (최악)thread k가 a[32*k] (a[0], a[32], …, a[992])모두 bank 0의 서로 다른 값 → 32 cycles
함정 "같은 bank에 여러 요청" = conflict가 아니다. 모두 같은 주소(같은 값)면 broadcast라 1 cycle이다. 같은 bank의 서로 다른 주소일 때만 직렬화된다. 또 bank conflict는 한 warp 안의 thread끼리만 따진다.

2D tile의 bank conflict와 padding: transpose-bankopt

__shared__ float mat[32][32];
mat[threadIdx.y][threadIdx.x] = ...;   // no bank conflict
... = mat[threadIdx.x][threadIdx.y];   // bank conflict

특정 threadIdx.y에서 threadIdx.x = 0…31인 warp가 mat[0][ty], mat[1][ty], …, mat[31][ty]를 읽는다. 원소 간격이 32이므로 모두 한 bank에 몰려 32-way conflict, 곧 최악의 경우다. transpose-block의 s_mat[tx][ty] 읽기가 바로 이 모양이다. global 쪽 coalescing을 고쳤더니 shared 안에서 최악의 conflict가 남은 것이다(shared에 저장하는 s_mat[ty][tx]는 문제없다).

해결책은 한 줄이다: __shared__ float mat[32][32+1]; 행마다 float 하나를 일부러 낭비하면 행 간격이 33이 되고, 한 행 내려갈 때마다 bank가 한 칸씩 밀린다. 그래서 같은 열의 32 원소가 32개 bank로 완벽히 분산된다.

__global__ void kernel_mat_transpose(float* C, const float* A, int N, size_t stride) {
    __shared__ float s_mat[32][32 + 1];    // 바뀐 곳은 이 한 줄뿐
    ...                                    // 나머지는 transpose-block과 동일
    C[indC] = s_mat[tx][ty];
}
  • tile의 논리 크기는 여전히 32×32다. thread block을 32×33으로 늘리는 것이 아니다. 33번째 열은 아무도 쓰지 않는다.
  • 추가 비용: 32 float = 128 B (총 32×33×4 = 4224 B)
  • 저장 s_mat[ty][tx]는 여전히 한 행을 연속으로 쓰므로 conflict가 없다.

CUDA bank opt 0.645 ms는 shared 복사 0.641 ms와 거의 같다. 기준선에 붙었으니 "아주 적합하게 최적화됐다"는 것이 교수님 결론이다. ROCm은 약간만 빨라졌다(옛 카드라서일 수 있음). 그래도 bank를 고려한 이 기법은 CUDA든 ROCm이든 자연스럽게 쓰는 것이 좋다고 했다.

  • shared memory 사용 목표: block 안 thread끼리의 통신(inter-thread communication), global 접근을 줄이기 위한 데이터 cache
  • 주의: shared memory is banked. warp 안 thread끼리만 문제가 되며, bank conflict 상황은 피해야 한다.
  • best performance와 비교: 여기서는 matrix copy와의 속도 비교. 최고 성능을 예측하고 그것과 비교하며 최적화 여부를 판단한다.
쉽게 말하면 전치 최적화는 세 단계다. ① global에서는 무조건 가로로 읽고 가로로 쓴다(coalescing). ② 세로로 뒤집는 일은 빠른 shared 안에서만 한다(block swap + [tx][ty]). ③ 그 세로 읽기가 한 bank에 몰리지 않게 행 폭을 33으로 비튼다(padding).
시험 포인트 단계별 시간이 왜 그렇게 바뀌는지 원인과 함께 쓸 수 있어야 한다. naive 1.084(흩어진 쓰기) → shared 1.133(쓰기 패턴 그대로, 단계만 추가) → block 0.796(global 양쪽 coalesced) → bank opt 0.645(shared 열 읽기의 32-way conflict 제거, 복사 0.641에 근접).

1주차 · 병렬 컴퓨팅과 Hello CUDA

CPU와 GPU의 설계 철학 차이를 목표, 코어·CU·캐시 구성, 적합한 작업 측면에서 서술하라.
CPU의 목표는 반응 시간(latency) 단축이다. 순차 처리에 집중하고, 복잡한 명령어를 빨리 처리하는 고성능 ALU, 대규모 CU, 대용량 캐시를 가진 큰 코어를 몇 개~수십 개 둔다. 워드 프로세서처럼 입력마다 즉시 반응해야 하는 대화형 작업에 맞다. GPU의 목표는 처리량(throughput) 확대다. 코어 하나의 성능과 무관하게 코어 수를 늘린다. 작고 단순한 ALU를 대량(1000개 이상 동시 실행)으로 배치하고, 간단한 CU 하나가 여러 ALU를 한꺼번에 제어하며, 캐시는 소규모다. thread pool을 효과적으로 관리해 단위 시간당 처리량을 크게 늘린다. 그래서 빅데이터 통계, 딥러닝 행렬 연산처럼 간단한 계산을 대규모 데이터에 반복하는 작업에 맞다.
대규모 병렬 컴퓨팅(MPC)이 가장 적합한 문제의 특징은 무엇이고, 왜 그런가? 응용 분야 두 가지를 예로 들라.
계산 하나하나는 비교적 간단하지만(사칙연산, sin·cos 정도) 매우 대규모로 반복해야 하는 문제다. GPU는 ALU 하나를 작고 단순하게 만든 대신 수를 극대화했기 때문에, 복잡한 계산 하나보다 같은 계산을 수많은 데이터에 동시에 적용할 때 강하다. 예: AI·딥러닝(곱셈·덧셈 위주의 거대한 행렬·벡터 연산, PyTorch·TensorFlow의 기반), 암호화·블록체인·암호화폐, 과학·공학 시뮬레이션(분자 생물학, 기상 예측 등).
CUDA란 무엇인지 정의하고, "범용 프로그래밍 모델"과 "툴킷"이라는 말의 의미를 설명하라.
CUDA는 Compute Unified Device Architecture의 약자로, 2006년 NVIDIA가 자사 GPU 전용으로 출시했다. 범용(general purpose)이란 GPU를 화면 출력에만 쓰지 않고 대규모 스레드를 실행하는 대규모 병렬 처리 코프로세서로 쓴다는 뜻이다. 툴킷이란 디바이스(컴퓨터 구조) + 프로그래밍 언어 + 컴파일러 + 라이브러리 등을 묶은 전체 세트라는 뜻이다. CUDA 드라이버가 GPU를 구동하고, CUDA 라이브러리가 API 함수를, CUDA 컴파일러(nvcc)가 확장된 언어를 제공한다. 가장 기본은 C/C++ API다.
빈칸: CUDA 커널 함수에는 ____ 설정자를 붙이고, kernel<<<1,16>>>() 같은 실행 문법을 ____ form이라 한다. 커널 안에서 각 스레드는 내장 변수 ____로 자기 번호를 얻는다.
__global__ / triple chevron(3중 꺽쇠 괄호) / threadIdx.x
실행 결과: hello-gpu.cu에서 launch를 kernel<<<4,4>>>();로 바꾸면 "hello from GPU" 줄은 몇 번 출력되고, 출력되는 threadIdx.x 값은 어떻게 되는가? <<<1,16>>>와 비교하라.
둘 다 4×4 = 1×16 = 16번 출력된다. <<<1,16>>>은 한 세트(블록)에 16개라서 threadIdx.x가 0~15로 한 번씩 나온다. <<<4,4>>>는 4세트 × 4개라서 threadIdx.x가 세트 안의 번호이므로 0,1,2,3이 네 번 반복된다. 앞뒤에는 "begin GPU kernel"과 "end GPU kernel"이 찍힌다. (세트 사이 순서는 보장되지 않는다.)
cudaDeviceSynchronize()의 역할과 반환값을 쓰고, hello-gpu.cu에서 커널 호출 뒤에 이 함수가 필요한 이유를 fflush(stdout)과 구분하여 설명하라.
원형은 cudaError_t cudaDeviceSynchronize(void);다. 모든 CUDA device가 앞서 요청받은 작업을 완료할 때까지 host를 블록시키고, 성공하면 cudaSuccess를 반환한다. 커널 launch는 GPU에 일을 요청할 뿐이므로, 동기화하지 않으면 GPU 작업(및 그 printf 출력)이 끝났다는 보장 없이 main이 다음 줄로 가거나 종료될 수 있다. 그래서 커널을 부른 뒤에는 반드시 동기화해서 완료를 보장한 다음 결과를 본다. fflush(stdout)는 CPU 쪽 표준 출력 버퍼를 비우는 것으로, GPU 완료와는 무관한 별개의 역할이다.
사지선다: 다음 중 옳지 않은 것은?

  2. 모든 CUDA 함수는 "cuda"로 시작하고 대부분 에러 코드를 리턴한다.
  3. 커널 함수 안에서 std::cout으로 출력할 수 있다.
  4. hipify-perl은 CUDA 소스를 HIP 코드로 변환한다.
③ — device 코드에서는 C++ stream을 지원하지 않아 "identifier "std::cout" is undefined in device code" 컴파일 에러가 난다. 커널 출력에는 C의 printf를 쓴다. ①은 맞다. .cu는 커널을 포함할 수 있다는 뜻이지 필수가 아니다.
계산: PC CPU 최대 성능을 4 TFLOPS, RTX 5090을 104 TFLOPS라 하면 GPU는 CPU의 약 몇 배인가? 슈퍼컴퓨터 하한(10 PFLOPS)에 이르려면 RTX 5090(일반 모드)이 약 몇 장 필요한가?
104 / 4 = 약 26배. 10 PFLOPS = 10,000 TFLOPS이므로 10,000 / 104 ≈ 약 97장(약 100장). 반면 AI 모드 B200(최대 9 PFLOPS)은 2장이면 하한을 넘는다. 실제로 CUDA GPU 4~수백 개를 연결해 슈퍼컴퓨터처럼 쓰는 추세다. 단, 모드가 다른 수치(일반 vs AI)를 섞어 비교하지 않도록 주의한다.
CUDA 코드를 AMD GPU에서 실행하려면 어떻게 하는가? hello-gpu.cu가 hello-gpu.hip으로 바뀔 때 달라지는 부분을 쓰라.
ROCm의 언어인 HIP은 CUDA와 거의 호환되어 많은 경우 "cuda" 접두사를 "hip"으로 바꾸면 된다. hipify-perl -o hello.hip hello.cu로 변환하고 hipcc -o hello.exe hello.hip으로 컴파일한다. 달라지는 곳은 #include "hip/hip_runtime.h" 추가와 cudaDeviceSynchronize → hipDeviceSynchronize뿐이다. __global__과 triple chevron <<<1,16>>>은 그대로다.

2주차 · 메모리 공간과 할당

CUDA 프로그램에서 host와 device의 메모리가 분리되어 있다는 것은 무슨 뜻이며, 그 때문에 전형적인 CUDA 프로그램은 어떤 3단계를 거치는지 서술하시오.
host = CPU + main memory, device = GPU + video memory이고, CPU ↔ video memory와 GPU ↔ main memory는 직접 연결되지 않는다(PCIe로만 연결). 그래서 데이터를 명시적으로 복사해야 한다. ① host CPU가 외부 데이터를 main memory에 읽고 main memory → video memory로 복사한다. ② 커널(device)이 video memory의 데이터를 GPU로 병렬 처리하고 결과를 video memory에 저장한다. ③ host CPU가 video memory → main memory로 복사한 뒤 출력·저장한다. GPU는 계산을, CPU는 I/O를 맡는다. 노트북처럼 물리적으로 메모리를 공유해도 개념적으로는 영역을 구분한다.
nvcc 명령만 실행했는데 main() 같은 순수 C++ 코드는 어떻게 컴파일되는가? NVCC의 처리 구조를 설명하시오.
NVCC는 .cu 소스를 CUDA 커널 코드(__global__ 등)와 순수 C++ 코드로 분리한다. 커널 코드는 NVCC가 직접 컴파일해 GPU용 실행 코드를 만들고, 순수 C++ 코드는 미리 설치된 C++ 컴파일러(clang/gcc/msvc)에 넘겨 CPU용 실행 코드를 만든다. 두 결과는 하나의 실행 파일에 함께 들어가고, 실행할 때 각각 CPU와 GPU로 보내진다. NVCC 설치 전에 C++ 컴파일러를 먼저 깔아야 하는 이유가 이것이다.
cudaMalloc은 왜 malloc처럼 주소를 반환하지 않고 (void**)&dev_ptr을 인자로 받는가?
거의 모든 CUDA 함수는 반환값으로 에러 코드(cudaError_t, 성공 시 cudaSuccess)를 돌려준다. 반환값 자리를 에러 코드가 차지하므로, 할당한 영역의 시작 주소는 인자로 받은 포인터 변수의 주소(&dev_ptr)에 써 넣는다. 포인터 변수의 주소이므로 타입은 void**이다. 이때 dev_ptr 변수 자체는 main memory에 있고, 그 값만 video memory 주소가 된다.
다음 코드 실행 후 dev가 가리키는 int 원소 하나의 값은? (16진수) 
int* dev;  cudaMalloc((void**)&dev, 4 * sizeof(int));
cudaMemset(dev, 0x77, 4 * sizeof(int));
0x77777777. cudaMemset은 byte 단위로 value를 채우므로 모든 byte가 0x77이 되고, 4-byte int 하나는 0x77777777이 된다. 원소 하나에 0x77이 들어가는 것이 아니다. 그래서 memset은 주로 0으로 clear할 때 쓴다.
cudaMallocHost는 malloc과 같은 main memory에 할당한다. 그런데도 cudaMallocHost를 쓰는 이유와 단점을 서술하시오.
malloc으로 잡은 영역은 OS가 관리하고 CUDA는 쓰기만 한다. cudaMallocHost로 잡은 영역(page-locked memory)은 CUDA가 직접 관리하고 OS에 빼앗기지 않으므로, CUDA 입장에서는 최대 효율로 쓸 수 있다(효율성). 단점은 OS가 그 영역을 다른 프로그램에 줄 수 없게 되어 OS 전체 성능이 떨어질 수 있다는 것이다(메인 메모리의 큰 비율을 잡을 때 문제가 된다). 해제는 cudaFreeHost로 한다.
get-symbol.cu에서 host 배열 A에 대해 아래를 실행했다. 출력 결과를 쓰시오. (A는 일반 float A[1024];, sizeA의 초기값은 0, cudaErrorInvalidSymbol = 13) 
if ((err = cudaGetSymbolSize(&sizeA, A)) != cudaSuccess)
    printf("cudaGetSymbolSize() failed: error code = %d\n", err);
printf("size=%zu\n", sizeA);
cudaGetSymbolSize() failed: error code = 13 size=0
A는 CUDA가 관리하는 device symbol이 아니라 main memory의 일반 배열이므로 cudaErrorInvalidSymbol(13)이 반환된다. 실패하면 *size는 변하지 않으므로 초기값 0이 그대로 남는다. 반대로 __device__ float devA[1024]였다면 size=4096이 나온다.
malloc으로 할당한 포인터 ptrA에 cudaPointerGetAttributes를 적용했을 때 type 값은?
  1. cudaMemoryTypeHost
  2. cudaMemoryTypeUnregistered
  3. cudaMemoryTypeDevice
  4. cudaMemoryTypeManaged
② — malloc 메모리는 CUDA가 관리하지 않는 일반 host memory라서 unregistered이고, device는 −1로 나온다. cudaMemoryTypeHost는 cudaMallocHost로 잡은 page-locked host memory, Device는 cudaMalloc, Managed는 cudaMallocManaged로 할당한 메모리다.
managed(unified) memory의 장점과 단점을 쓰고, 강의에서 실제 개발 시 권장한 방식을 서술하시오.
장점: CPU와 GPU 양쪽에서 같은 주소(devPtr = hostPtr)로 쓸 수 있어 cudaMemcpy를 직접 쓸 필요가 없고 코드가 간결하다. 단점: 하드웨어와 OS가 지원해야 하고(미지원 시 cudaErrorNotSupported), 필요할 때마다 CUDA가 자동으로 복사하므로 프로그래머가 모르는 사이에 큰 배열의 복사가 빈번히 일어나 느려질 수 있다. 권장: 초기 개발에는 써도 되지만, 안정화된 뒤에는 device memory를 직접 할당(cudaMalloc + cudaMemcpy)하는 전통적 방식을 선호한다. 해제는 cudaFree로 한다.
빈칸: ROCm으로 변환된 코드에서 symbol 인자는 hipMemcpyToSymbol(______(devA), A, sizeof(A))처럼 감싸지고, cudaMemAdvise와 형식이 같은 HIP 함수의 이름은 ______ 이다.
HIP_SYMBOL, hipMemAdvise_v2. 원래의 hipMemAdvise는 마지막 인자가 int device라서 cudaMemAdvise(cudaMemLocation location)와 형식이 맞지 않는다.

3주차 · 커널·오류 처리·시간 측정

NVCC의 컴파일 단위(unit of compilation)는 무엇이며, 각 단위를 어느 컴파일러가 맡을지 어떻게 구별하는가?
함수(function) 단위. 파일 단위(C/C++ 기본)나 라인 단위(asm) 대신 함수마다 CPU/GPU를 배정한다. 구별은 함수 앞의 prefix로 한다: __host__(CPU, default라 생략 가능), __global__(커널: host가 호출, device에서 실행), __device__(device가 호출, device에서 실행). __host__ __device__를 함께 쓰면 두 번 컴파일되어 양쪽에서 쓸 수 있다.
__device__ / __global__ 함수에 대한 설명으로 틀린 것은?
  1. 함수의 address를 가져올 수 없다
  2. 함수 내부에 static 변수를 선언할 수 없다
  3. __global__ 함수는 계산 결과를 float 등으로 return할 수 있다
  4. 재귀 호출은 되도록 사용하지 않는다
③ — 커널(__global__)은 반드시 void를 반환한다. 결과는 포인터로 받은 device 배열에 직접 쓴다. ②의 이유: 수많은 스레드가 동시에 실행되면 static 변수도 그만큼 device 메모리에 잡아야 해서 의미가 없다.
CPU용 kernel_cpu_vec_add(int idx, …)와 GPU용 kernel_vec_add(…)의 본문 차이와, 각각을 실행하는 방식을 비교하여 서술하라.
본문은 int i = idx; 대 int i = threadIdx.x; 한 줄만 다르다. CPU 버전은 인덱스를 인자로 받고 for 루프가 i = 0 … N−1을 차례로 넘기며 N번 호출한다(sequential, N 단위시간). GPU 버전은 kernel_vec_add<<<1, N>>>(…) 한 번의 launch로 N개 스레드가 동시에 실행되며, 각 스레드는 launch 때 자동 설정된 자기 threadIdx.x(0 … N−1)로 담당 원소를 고른다(massively parallel).
다음 순서로 CUDA 호출이 일어났다. ① cudaMalloc 실패(cudaErrorMemoryAllocation) ② cudaMemcpy 실패(cudaErrorInvalidValue) ③ cudaMemcpy 성공 ④ cudaPeekAtLastError() ⑤ cudaGetLastError() ⑥ cudaGetLastError(). ④⑤⑥이 각각 돌려주는 값은?
④ cudaErrorInvalidValue, ⑤ cudaErrorInvalidValue, ⑥ cudaSuccess. last error는 마지막 오류 1개만 남으므로 ②가 ①을 덮어쓰고, 성공한 ③은 지우지 않는다. Peek은 읽기만 하고, Get은 읽은 뒤 cudaSuccess로 reset하므로 두 번째 Get은 cudaSuccess다.
CUDA 커널 함수가 오류 코드를 직접 return하지 않는(void만 가능한) 이유와, 그 대신 계산 결과와 오류를 어떻게 전달하는지 서술하라.
CPU 함수는 1번 실행되어 return 값 1개를 돌려주지만, 커널은 한 번 launch에 예컨대 100만 개 스레드가 병렬 실행되므로 각자 반환하면 반환값(오류 코드)이 100만 개가 되어 받아 처리할 방법이 없다. 그래서 ① 계산 결과는 CUDA memory 영역의 배열/변수를 직접 update하고(예: float* devC 파라미터), ② 오류는 runtime이 last error에 기록해 두므로 launch 후 cudaDeviceSynchronize() 다음에 cudaPeekAtLastError()/cudaGetLastError()로 간접 확인한다.
오류 체크 매크로를 do { … } while (0)로 감싸는 이유와, #if defined(NDEBUG) 분기에서 release mode일 때 매크로가 어떻게 되는지 설명하라.
본문이 { … }로 끝나는 매크로를 함수처럼 CUDA_CHECK_ERROR();로 쓰면 세미콜론 때문에 syntax error가 날 수 있다(semi-colon problem, 예: if-else 사이). do-while(0)로 감싸면 매크로 전체가 한 문장이 되어 뒤의 ;가 while을 닫으므로 항상 OK이고, 딱 한 번만 실행된다. 대부분의 컴파일러는 release mode에 NDEBUG, debug mode에 _DEBUG를 정의하므로, release에서는 매크로를 0으로 정의해 0;이 되어 아무 일도 하지 않고(체크 생략, 약간 빠름), debug에서는 cudaGetLastError로 검사해 __FILE__, __LINE__과 함께 출력하고 exit(1)한다.
GPU 커널 시간을 다음처럼 쟀더니 커널 실행 시간과 다른 값이 나왔다. 무엇이 빠졌으며 왜 필요한가?
start = steady_clock::now(); kernel<<<1, N>>>(…); end = steady_clock::now();
cudaDeviceSynchronize();가 launch와 end = now() 사이에 빠졌다. kernel launch는 GPU에 일을 넘기고 곧바로 CPU로 돌아오므로, 동기화 없이 end를 읽으면 커널이 끝나기 전 시각이 기록되어 커널 시간 대부분이 빠진다. 또 간격 측정에는 바뀔 수 있는 system_clock이 아니라 monotonic한 steady_clock을 쓴다.

N = 3145728 (strtol이 3을 읽고 ptr이 'M' → 3 × 1024 × 1024), argc = 4, argv[0] = "./parse-argc.exe", argv[1] = "3M". 인자 없이 실행하면 argc = 1이므로 기본값 N = 1024가 나온다.
PTX와 compute capability가 무엇이며, 왜 -gencode=arch=compute_75,code=\"sm_75,compute_75\"처럼 sm과 compute를 함께 지정하는지 서술하라.
PTX(Parallel Thread Execution)는 일종의 중간 언어(가상 명령어)이고, compute capability는 GPU별로 PTX 버전을 구분하는 번호다(RTX 2070 = 7.5 → compute_75/sm_75). code=sm_75는 해당 GPU의 실제 기계어, code=compute_75는 PTX를 생성한다. 둘 다 exe에 넣으면 RTX 2070에서는 기계어를 바로 실행하고, 다른/새 GPU에서는 PTX를 just-in-time 컴파일해 실행할 수 있어 호환성이 확보된다. -arch=native는 장착 GPU용으로만 만들고 PTX는 생성하지 않을 수 있어 GPU 교체 시 실행이 안 될 수 있다.

time(NULL) / 초(seconds) / RAND_MAX(inclusive). 같은 seed면 같은 수열이 나오므로 srand(0)은 매번 같은 값이다. 강의 환경의 RAND_MAX는 2147483647(POSIX 예시는 32767).

4주차 · grid·block·thread와 AXPY

CUDA에서 grid–block–thread 계층 구조를 쓰는 이유를, 스레드 수와 코어 수의 관계를 들어 설명하시오.
GPU 코어는 1K~10K 수준인데 처리할 데이터와 스레드는 1M~1G 이상으로 보통 thread 개수 ≫ core 개수다. 그래서 thread를 block으로, block을 grid로 묶어 계층적으로 launch한다. block은 SM 하나에 통째로 배정되는 실행 단위이고(그래서 크기 상한이 있다), 블록 수가 SM 수보다 훨씬 많아도 queue-like 구조에서 빈 SM에 하나씩 배정하면 된다. 각 thread 안은 sequential code, thread 전체는 parallel로 실행된다.
dim3 dimGrid(100, 50, 1); dim3 dimBlock(4, 8, 8); 로 launch할 때 block 수, block당 thread 수, 총 thread 수는?
block 수 = 100×50×1 = 5,000, block당 thread = 4×8×8 = 256, 총 thread = 5000×256 = 1,280,000개.
gridDim(6), blockDim(4)인 1D launch에서 blockIdx.x = 4, threadIdx.x = 1인 스레드의 전역 인덱스는? 식과 함께 쓰시오.
idx = blockIdx.x * blockDim.x + threadIdx.x = 4 × 4 + 1 = 17. 전체 스레드는 24개(0~23)다.
N = 1G일 때 kernel_vec_add<<<1, N>>>(...)를 실행하면 어떻게 되는가? 이유와 올바른 launch 코드를 쓰시오.
컴파일은 되지만 실행 시 invalid argument error가 난다(GPU 시간 0 msec 뒤 CUDA_CHECK_ERROR가 잡음). block dim이 최대 1,024라는 제약을 넘었기 때문이다. 올바른 코드: dim3 dimBlock(1024,1,1); dim3 dimGrid((N + dimBlock.x - 1) / dimBlock.x, 1, 1); kernel_vec_add<<<dimGrid, dimBlock>>>(devPtrC, devPtrA, devPtrB, N); 1G면 1M개 블록이 된다.
N = 3000, blockDim.x = 1024일 때 gridDim.x와 총 스레드 수를 구하고, 커널에 if (i < N)이 필요한 이유를 서술하시오.
gridDim.x = (3000 + 1023) / 1024 = 4023 / 1024 = 3, 총 3,072 threads. 그중 i = 3000~3071인 72개는 배열 범위 밖이다. launch된 스레드 수(dimBlock.x × dimGrid.x ≥ N)와 배열 크기 N이 일치하지 않으므로, boundary check 없이는 배열 밖 메모리를 읽고 쓰게 된다. 그래서 커널이 N을 인자로 받아 i < N일 때만 계산한다.
nvcc로 컴파일할 때 CPU 쪽 코드에 -O2 최적화를 적용하려면 어떻게 해야 하며, GPU 쪽은 왜 따로 설정하지 않아도 되는가?
nvcc는 CPU·GPU를 따로 설정한다. CPU 코드는 host C++ compiler로 옵션을 전달해야 하므로 -Xcompiler -O2를 쓴다(그냥 -O2는 nvcc 자신의 옵션이 된다. CPU default는 -O0). GPU 코드는 default가 -O3(최대 최적화, 권장)라 별도 설정이 필요 없다. PTX 어셈블러는 필요하면 -Xptxas -O3로 준다.
GPU에서 kernel<<<1, 1>>>로 for 루프를 돌린 실험과 managed memory 실험의 결과가 느렸던 이유를 각각 설명하시오.
① single core: N = 1M에 34 ms(1G면 약 34 s 예상)로 CPU보다 훨씬 느리다. SP 하나는 ALU 수준의 약한 코어이고, GPU의 성능은 수많은 스레드의 병렬성에서 나오기 때문이다(테스트 목적 외에는 잘못된 코딩). ② managed memory: 1G에서 8 ms → 1,038 ms로 CPU보다도 느려졌다. 명시적 복사가 없어도 host↔device 데이터 이동이 숨어서 일어나 측정 구간에 들어갔기 때문으로 추정된다. 그래서 managed memory는 조심해서 써야 한다.
MAC/MAD와 FMA의 하드웨어 구현 차이를 식으로 쓰고, FMA의 장점을 쓰시오.
MAC/MAD: round( round(a*x) + y )로 반올림 2번. FMA(fused multiply-add, FMAC/FMADD): round( a*x + y )로 곱셈·덧셈을 한 단계(in one step)에 하고 반올림은 1번. 장점은 약간 빠르고 정밀도가 약간 올라간다는 것이다(deep learning 등에서 선호). C++/CUDA에서는 fmaf(float), fma(double)로 쓴다.
axpy-fma.cu에서 fmaf를 명시적으로 썼더니 GPU 시간은 그대로이고 CPU 시간은 687 ms → 1,705 ms로 늘었다. 가장 적절한 해석은?
  1. GPU에는 FMA 하드웨어가 없어서 효과가 없다
  2. 컴파일러가 일반 식도 이미 FMA로 바꾸고 있었고, CPU에서는 math library fmaf의 함수 호출 비용이 더해졌다
  3. FMA는 반올림을 2번 해서 느리다
  4. -O0로 컴파일해서 CPU가 느려졌다
② — 현대 최적화 컴파일러는 a*X[i]+Y[i](lerp 식조차)를 스스로 FMA 명령으로 바꾼다. 그래서 GPU는 차이가 없고, CPU는 명시적 fmaf()가 function call이 되어 더 느려졌다. 결론: 매뉴얼을 믿지 말고 직접 측정해 크로스 체크하라.
lerp f(t) = (1 − t)v₀ + t·v₁ 을 FMA 두 개로 쓰시오. (X[i] = v₀, Y[i] = v₁)
Z[i] = fmaf(t, Y[i], fmaf(-t, X[i], X[i])); 안쪽 fma = −t·v₀ + v₀ = (1−t)v₀, 바깥 fma = t·v₁ + (안쪽). 식을 (v₀ − t·v₀) + t·v₁로 바꿔 쓴 것이다.

5주차 · warp와 2차원 배열

[5주차] CUDA가 grid–block–thread 계층에서 thread block이라는 중간 단위를 둔 이유를 transparent scalability와 연결해 설명하시오.
CUDA 장치는 SM이 1~4개인 저가 기기부터 1000개 이상인 워크스테이션까지 다양하다. 같은 커널이 어디서나 돌아가야 하므로, 일을 thread block 단위로 쪼개 큐에 넣고 SM 1개가 block 1개씩 가져가 처리하게 했다. block들은 서로 순서와 무관하게(in any order) 실행되므로 SM이 많으면 동시에 더 많은 block을 처리해 빨라지고, 적으면 느릴 뿐 결과는 같다. 프로그램이 특정 SM 수에 묶이지 않는 것이 핵심이다.
[5주차] SM에 256-thread block 3개가 배정되었다. warp는 모두 몇 개이고, 어느 한 순간 실제로 실행되는 warp는 몇 개인가?
block당 256 / 32 = 8 warps, 전체 3 × 8 = 24 warps. 그러나 SM unit의 core가 32개뿐이므로 어느 순간이든 24개 중 1개의 warp만 instruction fetch·실행된다. 나머지는 관리(resident)만 되며 스케줄러가 번갈아 고른다.
[5주차] GPU가 100 clock 이상 걸리는 메모리 지연을 어떻게 숨기는지 warp scheduling, zero-overhead, score-boarding을 써서 서술하시오.
메모리 read/write를 만난 warp는 waiting 상태로 돌리고, operand가 모두 준비된 ready warp 중 하나를 scheduler가 우선순위에 따라 즉시 실행한다(time sharing). SM에는 65,536개 이상의 레지스터가 있어 각 warp가 자기 레지스터를 그대로 가지고 있으므로 전환 비용이 거의 0이다(zero-overhead). score-boarding은 instruction buffer에 있는 모든 instruction의 register operand 준비 상태를 추적해 waiting/ready를 판정한다. 메모리 지연 자체를 줄이는 것이 아니라, 그 시간에 다른 warp를 실행해 core가 놀지 않게 하는 것이다.
[5주차] 메모리 접근 100 cycle, 명령 4개마다 메모리 접근 1번인 전형적인 CUDA 프로그램에서 core를 쉬지 않게 하려면 warp가 몇 개 필요한가?
100 / 4 = 25 warps. 한 warp가 메모리를 기다리는 100 cycle 동안 다른 warp들이 4개씩 명령을 실행해 빈 시간을 메운다.
[5주차] gridDim(3,5), blockDim(4,3)에서 blockIdx = (2,1), threadIdx = (3,2)인 thread의 전역 인덱스 (gx, gy)와, WIDTH = 12인 1D 배열에서의 인덱스 i를 구하시오.
gx = 2 × 4 + 3 = 11, gy = 1 × 3 + 2 = 5 → (11, 5). 행렬로는 row 5, col 11이다. i = gy × WIDTH + gx = 5 × 12 + 11 = 71.
[5주차] 10,000 × 10,000 행렬을 32 × 32 block으로 처리할 때 CUDA_PRINT_CONFIG_2D(NROW, NCOL)의 출력 4줄을 쓰시오.

10000 / 32 = 312.5 → 313, 313 × 32 = 10,016. 오른쪽 16열·아래 16행의 thread는 if 문으로 아무 일도 하지 않는다.
[5주차] 첫 커널의 실행 시간을 잴 때 CUDA_WARM_UP()이 필요한 이유와 그 구현을 쓰시오.
CUDA/ROCm은 slow start를 한다. exe가 실행돼도 GPU를 바로 준비하지 않고, 첫 CUDA 함수 호출이나 첫 kernel 호출 때 실제로 시동을 건다(컨텍스트 준비 등). 그래서 첫 커널을 측정하면 이 시동 시간이 섞인다. 구현: cudaFree(0);로 dummy CUDA 함수 호출, __hidden_kernel_warmup<<<1, 1>>>();로 아무 일도 하지 않는 dummy kernel 호출. 강의에서 CUDA 10,000²는 0.864 → 0.801 ms가 되었다.
[5주차] 행렬 덧셈 커널에서 row와 col 계산의 x, y를 뒤바꾸었다. 결과 값은 어떻게 되고 성능은 어떻게 되는가? 이유를 DRAM burst와 coalescing으로 설명하시오.
정방 행렬 덧셈이면 모든 원소가 결국 한 번씩 더해지므로 결과 값은 같다(그래서 버그를 찾기 어렵다). 그러나 느려진다(CUDA 10,000²: 0.801 → 1.281 ms). 올바르면 한 warp의 이웃 32 thread가 index = y*WIDTH + x로 연속된 32개 주소를 읽어 DRAM burst·coalescing으로 한 번에 전송된다. 뒤바꾸면 index = x*WIDTH + y가 되어 32 thread가 WIDTH 간격으로 흩어진 주소를 건드리므로 메모리 접근이 32번으로 쪼개진다.
[5주차] 하드웨어가 32B 단위로 전송할 때, 32 thread가 4-byte word를 주소 116~244에서 읽는 경우 필요한 transaction 수는? 128~256이면?

  2. 5번 / 4번
  3. 4번 / 5번
  4. 8번 / 4번
② — 128~256은 32B 경계에 정렬되어 128~160~192~224~256의 4번. 116~244는 96~128부터 224~256까지 걸쳐 5번이 필요하고, 첫·끝 segment의 일부는 가져와서 버린다(1.2배). 64B 단위면 2→3번, 128B 단위면 1→2번으로 손해가 더 커진다.
[5주차] cudaMallocPitch의 pitch 인자와 width 인자의 차이, 그리고 (row, col) 원소의 주소를 구하는 식을 쓰시오. 실제 장치에서 10,000개 float 한 행의 pitch가 40,448이었다면 stride는?
width는 요청한 한 행의 유효 데이터 크기(byte)이고, pitch는 boundary 정렬을 위한 padding까지 포함한 다음 행까지의 실제 간격(byte)으로 함수가 반환한다. 주소: T* pElem = (T*)((char*)baseAddr + row * pitch) + col; (width 대신 pitch 사용). stride = pitch / sizeof(float) = 40,448 / 4 = 10,112 원소. boundary는 시스템마다 달라서 강의 그림의 256B 가정(10,048)과 다르다. 그래서 반환된 pitch를 써야 한다.

6주차 · 3D·메모리 계층·shared

[계산] dim3 dimImage(300, 300, 256) 데이터를 dim3 dimBlock(8, 8, 8)로 처리한다. dimGrid와 실제 launch되는 전체 thread 수(축별), 아무 일도 하지 않는 thread가 생기는 이유를 쓰시오.
dimGrid = ⌈300/8⌉ × ⌈300/8⌉ × ⌈256/8⌉ = 38 × 38 × 32. 전체 thread = 304 × 304 × 256. 300은 8의 배수가 아니라서 x, y축 끝에서 4개씩(304 − 300) thread가 남는다. 이 thread들은 경계 검사 if (gx < dimImage.x && gy < dimImage.y && gz < dimImage.z)에 걸려 아무것도 하지 않는다(do nothing threads). 256은 8의 배수라 z축에는 남는 thread가 없다.
[계산] width = 300, height = 300인 3D float 배열에서 (z, y, x) = (2, 1, 5)인 원소의 ① compact 배열의 1D 인덱스와 ② pitch = 1536 byte인 cudaMalloc3D 배열에서 ptr로부터의 byte offset을 구하시오.
① i = (z × HEIGHT + y) × WIDTH + x = (2 × 300 + 1) × 300 + 5 = 601 × 300 + 5 = 180305.
② offset = (z × ysize + y) × pitch + x × sizeof(float) = (2 × 300 + 1) × 1536 + 5 × 4 = 601 × 1536 + 20 = 923156 byte. pitch에 이미 padding이 들어 있으므로 width × 4 = 1200을 곱하면 틀린다.
[서술] cudaPitchedPtr의 네 필드(pitch, ptr, xsize, ysize)의 의미와 단위를 쓰고, 300×300×256 float 배열을 512 byte 경계로 정렬하는 시스템에서 각 값을 구하시오. C++ new float[300*300*256]로 만든 배열과 무엇이 다른가?
pitch: 다음 행까지의 간격(byte) / ptr: 실제 시작 주소 / xsize: 한 행의 유효 폭(byte) / ysize: 한 slice의 행 수(elements). cudaMalloc3D: xsize = 300 × 4 = 1200, pitch = ⌈1200/512⌉ × 512 = 1536, ysize = 300. C++ 배열은 padding 없이 compact하게 잡히므로 pitch = xsize = 1200이다. depth는 주소 계산에 필요 없어 구조체에 없다. 정렬 경계(32B~1024B)는 CUDA version, system, hardware에 따라 달라지므로 cudaMalloc3D가 돌려주는 실제 pitch를 써야 한다.
[사지선다] make_cudaExtent(w, h, d)에 대한 설명으로 옳은 것은?
  1. w, h, d 모두 원소 개수로 넣는다
  2. w는 byte 단위, h와 d는 원소 개수로 넣는다
  3. w, h, d 모두 byte 단위로 넣는다
  4. 메모리를 할당하고 pitch를 돌려준다
② — width만 byte 단위다(그래서 예제는 dimImage.x * sizeof(float)를 넣고 변수 이름도 extentInByte). 교수님이 두 번 "주의"라고 강조한 부분이다. ④는 cudaMalloc3D의 역할이고, make_cudaExtent는 크기 구조체만 만든다.
[서술] 300×300×256 실험에서 cudaMalloc3D(pitched) 버전(0.371 ms)이 compact cudaMalloc 버전(0.212 ms)보다 느렸고, 999³에서는 7.959 ms 대 8.025 ms로 약간 빨랐다. 이 결과를 해석하시오.
pitched 버전은 각 접근마다 구조체에서 ptr·pitch·ysize를 꺼내 char* 단위 byte 주소를 계산해야 해서 오버헤드가 있다. 문제 크기가 작으면 이 오버헤드가 행 정렬의 이득보다 커서 더 느리고, 크기가 크면 정렬 이득이 드러나 약간 유리해진다. 결론: 3D API를 쓴다고 성능이 보장되지 않으며, configuration에 따라 다르므로 항상 테스트해 봐야 한다.
[빈칸] 다음 표를 채우시오. int var; → (①) / int array[10]; (커널 안) → (②) / __shared__ int s; → shared, scope (③) / __constant__ int c; → constant, penalty (④). 또 register가 모자라면 무슨 일이 생기는가?
① register(scope thread, 1x) ② local memory(scope thread, 100+x) ③ block(lifetime block, 1x) ④ 1x(scope grid, lifetime application). register가 모자라면 자동으로 local memory를 쓴다. local memory는 실제로 global memory(off-chip DRAM)에 있어서 속도가 크게 떨어진다.
[서술] local memory와 shared memory를 위치, 공유 범위, 속도 면에서 비교하시오. "local"이라는 이름 때문에 생기는 오해는 무엇인가?
local memory: thread 하나만 쓰는 공간이지만 물리적으로는 global memory(device DRAM, off-chip) 안에 있어 느리다(100+x). 커널 안의 자동 배열이나 register spill이 여기에 간다. shared memory: SM 안(on-chip)에 있는 scratchpad memory로, 같은 block의 thread들이 공유하고 매우 빠르다(1x). 프로그래머가 __shared__로 명시적으로 선언해 쓴다. 오해: "local = 가까운 빠른 메모리"가 아니다. global과 같은 메모리에서 나 혼자 쓰는 영역일 뿐이다.
[계산] deviceQuery 결과가 "Total number of registers available per block: 65536", "Maximum number of threads per block: 1024"일 때, block을 1024 thread로 띄우면 thread당 쓸 수 있는 register는 최대 몇 개인가? 이를 넘으면 어떻게 되는가?
65536 / 1024 = 64개. 커널이 이보다 많은 register를 필요로 하면 넘치는 변수는 local memory로 가서(spill) 느려진다. 그래서 device query로 자원 한도를 확인해야 한다.
[서술] __device__ float devX[N];에서 N을 64M에서 256M으로 키우자 빌드가 실패했다. 어느 단계의 오류이며, 교수님이 제시한 해결 방향과 cudaGetSymbolAddress의 역할은?
컴파일이 아니라 link 단계 오류다(Windows: LNK1248 이미지 크기 초과, Linux: ld returned 1 exit status). 정적 심볼 배열은 크기 한계가 있으므로 큰 메모리는 cudaMalloc 동적 할당을 선호한다. cudaGetSymbolAddress는 심볼의 device 주소를 얻어 ToSymbol/FromSymbol 대신 일반 cudaMemcpy를 쓰게 해 준다. 이렇게 짜 두면 나중에 그 주소 자리에 cudaMalloc한 주소만 넣으면 되므로 동적 할당으로 쉽게 바꿀 수 있다. 크기 한계 자체를 풀어 주는 함수는 아니다.
[서술] shared memory 버전 adjacent difference 커널에서 ① __syncthreads()가 없으면 생기는 문제, ② tx == 0 예외가 필요한 이유, ③ 일반 thread의 global/shared 접근 횟수를 naïve 버전과 비교하시오.
① s_Buf[tx-1]은 이웃 thread가 쓴 값이다. warp마다 실행 속도가 달라서, 이웃 warp가 아직 쓰지 않은 칸을 먼저 읽을 수 있다(race condition). barrier로 같은 block의 모든 thread가 load를 마칠 때까지 기다려야 한다.
② tile은 자기 block의 원소만 담는다. block의 첫 thread에게 필요한 A[i−1]은 앞 block의 tile에 있어 shared로 볼 수 없으므로 global에서 직접 읽는다(B[i] = s_Buf[tx] - A[i-1]). 배열 전체 첫 원소(i == 0)는 0.0을 빼는 별도 예외다.
③ naïve: global read 2, global write 1. shared: global read 1, shared read 2, global write 1.
[사지선다] adjacent difference 실험에서 최신 CUDA GPU의 global-only 버전(5.818 ms)이 shared 버전(6.455 ms)보다 빨랐다. 옳은 해석은?
  1. shared memory는 global보다 원래 느리다
  2. __syncthreads()가 block 사이까지 동기화해서 느려졌다
  3. 컴파일러가 L1/L2 cache를 적극 활용해 단순한 global 코드도 빨라졌다. 복잡한 문제에서는 shared가 확실히 빠르다
  4. shared memory는 앞으로 쓸 필요가 없다
③ — 최신 device는 compiler가 L1/L2 cache를 적극 사용하므로 단순한 문제에서는 global-only가 shared 수준이거나 더 빠를 수 있다. device마다 test가 필요하다. 오래된 실험(69.164 ms → 47.299 ms)에서는 shared가 확실히 빨랐고, 교수님도 "복잡한 경우에는 shared를 쓰면 확실히 빠르다"고 했다. ②: __syncthreads()는 같은 block 안만 동기화한다.

7주차 · shared 활용·복사·전치

adj-diff-overuse.cu는 결과 B[i]를 쓴 뒤 __syncthreads()를 한 번 더 호출한다. 결과는 맞는데 CUDA에서 6.455 ms → 6.675 ms로 느려졌다. 이유와, 그렇다면 첫 번째 barrier도 빼도 되는지 서술하시오.
barrier는 block의 모든 thread가 도착할 때까지 멈추는 heavy operation이다. 두 번째 barrier 뒤에는 shared 데이터를 읽는 코드가 없어 보장하는 것이 없고, 가장 느린 thread를 기다리는 비용만 늘어난다. 첫 번째 barrier는 빼면 안 된다. s_Buf[tx-1]은 다른 thread가 쓴 값이므로, 그 쓰기가 끝났음을 보장하지 않으면 race condition이 생긴다. 원칙: 필요한 데이터 의존성에만 barrier를 쓰고 overuse하지 않는다(ROCm에서는 차이가 거의 없었다. 하드웨어마다 다름).
[계산] extern __shared__ float s_Buf[];를 쓰는 커널을 blockDim = (256, 1, 1)로 launch한다. thread당 float 1개가 필요하다면 triple chevron의 세 번째 인자 값은? 또 sharedMemPerBlock = 49152, maxThreadsPerBlock = 1024인 GPU에서 thread 하나당 쓸 수 있는 shared는 최대 몇 byte인가?
256 × sizeof(float) = 1024 (byte, block 하나당). 원소 수 256이나 grid 전체 크기가 아니다. 두 번째는 49152 / 1024 = 48 byte(float 12개).
__shared__ int* ptr;에 대한 설명으로 옳은 것은?
  1. ptr은 shared memory의 변수만 가리킬 수 있다
  2. ptr 변수 자체가 shared memory에 위치하며, global·constant 등 어느 공간의 주소든 담을 수 있다
  3. ptr은 register에 놓이고 shared 변수를 가리킨다
  4. 커널 인자로 넘어온 포인터는 shared memory 주소로 가정된다
② — Pointers are NOT typed on memory space. __shared__는 포인터가 "사는 곳"이다. ④는 틀렸다. 커널 인자 포인터는 global memory로 가정한다. 같은 warp에서 포인터가 서로 다른 공간을 가리키면 옛 CUDA는 crash, 지금은 성능 저하가 생긴다.
[계산] N = 10000인 float 행렬을 cudaMallocPitch로 잡았더니 dev_pitch = 40448이었다. A[2][5]의 (1) byte offset과 (2) stride 기준 index를 구하시오.
(1) offset = y·dev_pitch + x·sizeof(float) = 2·40448 + 5·4 = 80916 byte
(2) stride = 40448 / 4 = 10112 → idx = 2·10112 + 5 = 20229 (byte offset / 4와 같다). 한 줄 아래로 갈 때 N(10000)이 아니라 stride(10112)만큼 건너뛴다.
강의에서 행렬 복사를 모든 행렬 연산의 "theoretical limit / best score"라고 부른 이유를 쓰고, 새로 만든 행렬 연산이 복사보다 빠르게 측정되면 어떻게 판단해야 하는지 서술하시오.
어떤 행렬 연산도 원소마다 최소한 한 번 읽고 한 번 쓴다. 복사는 이 최소 작업만 하므로 같은 조건에서 가장 빠르다. 그래서 최적화한 연산이 복사 시간에 가까울수록 잘 최적화된 것이다. 복사보다 빠르다면 계산을 빠뜨렸거나 잘못 구현한 것이니 결과부터 다시 확인한다. 속도보다 정답 확인이 먼저다.
naive 전치(1.084 ms)가 복사(0.616 ms)보다 느린 이유와, shared tile을 거치는 transpose-shared(1.133 ms)가 전혀 개선되지 않은 이유를 메모리 접근 패턴으로 서술하시오.
한 warp는 threadIdx.x가 연속인 thread들이다. 읽기 indA = gy*stride + gx는 연속 주소라 coalesced다. 쓰기 indC = gx*stride + gy는 thread마다 stride(10112)씩 떨어져 흩어진 쓰기가 된다. transpose-shared는 tile을 거치지만 출력 index indC가 그대로라 쓰기 패턴이 같다. shared를 왕복하는 단계와 barrier 비용만 늘어 오히려 약간 느려졌다.
[빈칸] transpose-block.cu에서 __syncthreads(); 다음 부분을 완성하시오.
gy = blockIdx.__ * blockDim.x + threadIdx.__;
gx = blockIdx.__ * blockDim.y + threadIdx.__;
C[gy * stride + gx] = s_mat[__][__];
gy = blockIdx.x * blockDim.x + threadIdx.y;
gx = blockIdx.y * blockDim.y + threadIdx.x;
C[gy*stride + gx] = s_mat[tx][ty];
block 위치만 교환하고 thread 위치는 그대로 둔다. 그래서 threadIdx.x가 출력 열 방향을 맡아 쓰기도 연속이 된다. 전치는 tile 안의 [tx][ty] 읽기가 맡는다.
32 bank shared memory에서 한 warp(threadIdx.x = 0…31)가 다음과 같이 float 배열을 읽는다. n-way conflict를 각각 쓰시오. (가) a[tx] (나) a[0] (다) a[2*tx] (라) a[16*tx] (마) a[32*tx]
(가) 없음, 1 cycle (나) broadcast, 1 cycle: 같은 값 하나라 conflict 아님 (다) 2-way: tx와 tx+16이 같은 bank (라) 16-way: 짝수는 bank 0, 홀수는 bank 16 (마) 32-way: 모두 bank 0의 서로 다른 원소, 32 cycles
__shared__ float s_mat[32][32];을 s_mat[32][32+1];로 바꾸면 전치가 0.796 ms → 0.645 ms로 빨라진다. 그 원리와 비용을 서술하시오.
원소 s_mat[r][c]의 bank는 (행폭·r + c) % 32다. 행폭 32면 열 읽기 s_mat[tx][ty](tx = 0…31)의 bank가 전부 ty로 같아 32-way conflict가 난다. 행폭 33이면 bank = (r + c) % 32라 행마다 한 칸씩 밀려 32개 bank로 완전히 분산된다. 비용은 행마다 float 1개, 32×4 = 128 B(총 4224 B)뿐이다. 논리 tile과 block 크기는 32×32 그대로다. 결과 0.645 ms는 shared 복사 0.641 ms에 근접한다.

헷갈리는 쌍구분 포인트
latency vs throughputCPU = 반응 시간(latency) 단축, 순차·대화형 작업. GPU = 처리량(throughput) 확대, 대규모 데이터 병렬. GPU가 "무조건 빠른" 것이 아니다.
multi-core CPU vs many-core GPUmulti-core: 고성능 코어 2~32+개, 코어마다 큰 CU·ALU, 대용량 캐시. many-core: 단순 ALU 1,024~16,384+개, CU 하나가 여러 ALU를 제어, 소규모 캐시.
OpenMP vs OpenCLOpenMP(Open Multi-Processing) = 멀티 코어 CPU용, 쉬움. OpenCL(Open Computing Language) = Khronos, CPU/GPU/DSP/FPGA 범용, 복잡해서 초보자에게 어려움.
cudaDeviceSynchronize vs fflush(stdout)cudaDeviceSynchronize = GPU가 앞서 요청받은 작업을 완료할 때까지 host가 기다림(cudaSuccess 반환). fflush = CPU 표준 출력 버퍼 비우기. 서로 대체할 수 없다.
<<<1,16>>> vs <<<4,4>>>둘 다 총 16번 실행. threadIdx.x는 세트(블록) 안의 번호라서 1,16은 0~15, 4,4는 0~3이 4번 반복된다.
.cu에 커널이 꼭 있어야 하나아니다. .cu = C/C++ + (선택적) CUDA 커널. C/C++만 있어도 nvcc가 컴파일한다. 커널 안에서는 printf는 되지만 std::cout은 컴파일 에러다.
cudaMalloc vs cudaMallocHostcudaMalloc은 video memory에 할당하고 cudaFree로 해제한다. cudaMallocHost는 main memory에 page-locked로 할당하고 cudaFreeHost로 해제한다. 둘 다 clear하지 않는다.
포인터 변수의 위치 vs 가리키는 곳main()의 int* dev_ptr 변수 자체는 main memory에 있고, cudaMalloc 후 그 값이 video memory 주소가 된다. 그래서 host 코드에서 역참조하면 안 된다.
cudaMemcpyToSymbol vs cudaMemcpyToSymbol/FromSymbol은 __device__ 변수 이름(symbol)을 받고, 방향은 함수 이름으로 정해진다. cudaMemcpy는 주소를 받고 방향(cudaMemcpyKind)을 인자로 적는다. 크기는 둘 다 byte 수다.
memset value vs 원소 값value는 byte 단위로 채워진다. 0x77을 주면 int 원소는 0x77777777이 된다.
cudaMemoryTypeHost vs UnregisteredHost는 cudaMallocHost로 잡은 page-locked 메모리, Unregistered는 malloc으로 잡은 일반 host 메모리다(device = −1).
managed memory 해제·flagscudaMallocManaged로 잡은 메모리는 cudaFree로 해제한다(FreeHost 아님). flags 기본값은 cudaMemAttachGlobal(device), 다른 하나는 cudaMemAttachHost다.
__global__ vs __device____global__: host가 호출 → device에서 실행(커널, launch <<< >>>, 반드시 void). __device__: device가 호출 → device에서 실행. host는 __device__를 직접 부를 수 없다
cudaGetLastError vs cudaPeekAtLastError둘 다 마지막 오류 1개를 돌려준다. Get은 cudaSuccess로 reset, Peek은 reset하지 않음. 성공한 API 호출은 last error를 지우지 않는다
cudaGetErrorName vs cudaGetErrorStringName은 코드 이름(cudaErrorMemoryAllocation), String은 설명(out of memory). 둘 다 const char*, 잘못된 코드면 NULL
error 상태의 단위: CPU thread vs GPU threadlast error는 host(CPU) thread마다 하나씩 관리된다. 커널 안의 수많은 GPU 스레드마다 있는 것이 아니다
system_clock vs steady_clocksystem_clock: UNIX calendar clock, 바뀔 수 있음(현재 날짜·시각용). steady_clock: 부팅 이후, monotonic(간격 측정용). duration = end − start (슬라이드의 start − now() 식은 개념 표기)
code=sm_XX vs code=compute_XXsm_XX: 해당 아키텍처의 실제 GPU 기계어. compute_XX: PTX(중간 언어) → 다른 GPU에서 JIT 컴파일. arch=compute_XX는 기반 아키텍처 지정
blockDim vs gridDimblockDim = block 하나의 thread 수(최대 1,024), gridDim = grid 하나의 block 수. 전역 인덱스에 곱하는 것은 blockDim.x다
dim3 vs uint3크기(gridDim, blockDim)는 dim3, 위치(blockIdx, threadIdx)는 uint3. 둘 다 unsigned int x, y, z. dim3는 생략 성분이 1로 채워진다
dimGrid = N / B vs (N + B − 1) / B앞은 내림이라 N이 B의 배수가 아니면 스레드가 모자란다. 뒤가 올림(⌈N/B⌉)이고, 남는 스레드는 if (i < N)으로 걸러낸다
컴파일 성공 vs 유효한 launch<<<1, N>>>(N > 1024)은 컴파일되지만 실행 시 invalid argument가 난다. 커널이 실행되지 않으므로 GPU 시간은 0 msec
MAC/MAD vs FMAMAC/MAD는 round(round(a*x)+y)로 반올림 2번, FMA는 round(a*x+y)로 1번. 명시적 fmaf가 항상 빠른 건 아니다(컴파일러 자동 FMA, CPU 함수 호출 비용)
template 커널 vs class member 커널kernel에 template 적용은 가능, class member로 만드는 것은 불가. class의 host 멤버 함수 안에서 launch하는 것은 된다
warp(32 thread) vs SM이 관리하는 warp 수warp는 core 32개가 동시에 실행하는 묶음. SM은 24개, 2048 thread 이상을 관리하지만 한 순간 실행은 unit당 1 warp
warp id vs threadIdx / 32warp id는 SM 안 번호라 globally unique가 아니고, 부여 규칙은 system dependent. 함수가 없어 PTX(%warpid, %laneid)로 읽는다. CUDA warp는 항상 32, ROCm은 64(서버)/32(소비자)
(row, col) vs (x, y)행렬 위치 (row, col) = 좌표 (y, x). row = gy = blockIdx.y*blockDim.y+threadIdx.y, col = gx. 뒤바꾸면 결과는 같아도 coalescing이 깨져 느려짐
pitch vs width vs stridewidth = 요청한 한 행의 유효 byte, pitch = padding 포함 다음 행까지 byte(반환값), stride = pitch / sizeof(T) 원소 수. cudaMemcpy2D의 width는 byte, height는 행 수
cudaMalloc + cudaMemcpy vs cudaMallocPitch + cudaMemcpy2DcudaMalloc은 연속 1D(시작만 256B 정렬, 각 행 시작은 어긋날 수 있음). pitched 메모리는 반드시 cudaMemcpy2D로 양쪽 pitch를 주고 복사해야 padding을 건너뛴다
경계 검사 커널 vs oversized 커널if를 뺄 수 있는 조건: 가로 stride ≥ x thread 수 그리고 세로 행 수 ≥ numThread.y(그래서 높이를 numThread.y로 할당). 남는 영역 값은 버린다
cudaMalloc3D vs make_cudaPitchedPtrcudaMalloc3D는 device 메모리를 새로 할당하고 실제 pitch를 채워 준다. make_cudaPitchedPtr는 이미 있는 포인터(주로 host)에 pitch·xsize·ysize를 붙인 구조체만 만든다(할당 없음)
make_cudaExtent의 w vs h, dw(width)만 byte 단위(x * sizeof(float)), h·d는 원소 개수. cudaPitchedPtr도 pitch·xsize는 byte, ysize는 원소(행) 수
local memory vs shared memorylocal: thread 전용이지만 실제로는 global(off-chip DRAM)에 있어 느림(100+x). 커널 안 자동 배열·register spill이 감. shared: SM 안 scratchpad, block 공유, 빠름(1x), __shared__로 명시
__constant__ vs C++ const__constant__는 CUDA 메모리 공간(per-grid, thread는 read-only, 작고 빠름). host에서 cudaMemcpyToSymbol로 값을 갱신할 수 있다. 영원히 못 바꾸는 상수라는 뜻이 아니다
__syncthreads() vs cudaDeviceSynchronize()__syncthreads(): 커널 안, 같은 block의 thread끼리 barrier(intrinsic, heavy operation). cudaDeviceSynchronize(): host에서 device의 작업 전체가 끝나기를 기다림
i == 0 예외 vs tx == 0 예외 (adj-diff shared)i == 0: 배열 전체 첫 원소, A[−1]이 없어 0.0f를 뺌(B[0] = A[0]). tx == 0: 각 block의 첫 thread, A[i−1]이 tile 밖이라 global에서 직접 읽음
launch 세 번째 인자 sizeInByte vs 원소 수 / grid 전체 크기block 하나당 동적 shared memory byte 수. blockDim 512, float면 2048. block 크기를 바꾸면 같이 바꾼다.
__shared__ int* ptr: 포인터가 사는 곳 vs 가리키는 곳수식어는 ptr 변수의 위치(shared). 가리키는 대상은 아무 공간이나 가능. 커널 인자 포인터는 global로 가정한다.
broadcast vs bank conflict같은 bank라도 같은 주소면 broadcast(1 cycle). 같은 bank의 다른 주소일 때만 n-way로 직렬화된다. warp 안에서만 따진다.
transpose-shared vs transpose-blockshared를 거치기만 하면(출력 index 그대로) 쓰기가 흩어져 오히려 느려진다. block 위치 교환 + tile 안 [tx][ty] 읽기로 global 양쪽을 coalesced로 만들어야 빨라진다.
s_mat[32][33] padding vs tile/block 크기 변경block·논리 tile은 32×32 그대로. 저장 행 간격만 33이라 bank가 한 칸씩 밀린다. 비용은 128 B.
cudaMemcpy2D가 가장 빠름 vs 행렬 연산의 기준복사 API(0.514 ms)는 단순 복사만 가능해 전치·곱셈에 못 쓴다. 비교 기준과 개선 대상은 shared tile 커널이다.
