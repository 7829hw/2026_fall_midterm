00왜 DBMS가 필요한가

1주차 · 영화 대여점 rented.txt 예시

영화 대여점을 차렸다고 생각해 봅시다. 처음엔 메모장 파일 rented.txt 하나에 “Customer: M. Han, Rented: Avengers, Due: Sep. 2, 2026”처럼 적으면 충분해 보입니다. 쓰기 쉽고, 추가·삭제도 간단하죠. 하지만 가게가 커지면 문제가 여섯 가지 터집니다. 그리고 이 여섯 가지 문제를 해결하려고 만든 것이 바로 DBMS입니다. 이 표 하나가 이 과목 전체의 지도입니다.

문제파일로 하면 생기는 일DBMS의 해결책 (개념)
① 질의 (Query)“연체된 디스크가 있나?” 같은 질문을 텍스트 검색으로는 할 수 없음스키마와 데이터 분리, DML, SQL
② 무결성 (Integrity)오타(M. Ham, Deu), 없는 날짜(Oct. 35), 필드 순서 뒤섞임무결성 제약조건, 데이터 타입
③ 다중 사용자John과 Mary가 동시에 파일을 열고 저장하면 John의 기록이 사라짐직렬성(Serializability), 동시성 제어
④ 크래시500건 중 250건만 고쳤는데 컴퓨터가 꺼짐 → 반쯤 고쳐진 상태트랜잭션, 커밋, 롤백, 회복 (원자성 = 전부 아니면 전무)
⑤ 보안고객 이름은 숨기고 대여 횟수만 보여 주기가 불가능보안, 권한, 뷰(View)
⑥ 효율파일이 테라바이트급이 되면 편집도 검색도 너무 느림인덱스, 질의 최적화, 튜닝
쉽게 말하면 파일 시스템을 쓰면 보안, 동시성 제어, 스키마 변경, 인덱스 같은 기능을 프로그램마다 직접 다 만들어야 합니다. 많은 응용이 똑같이 필요로 하니까, 이걸 한 번에 제공하는 소프트웨어를 만들어 팔자 → 그게 DBMS입니다.

응용 프로그램은 DB에 두 가지 요청을 보냅니다. 질의(Query)는 주로 데이터를 읽어 오는 것이고, 트랜잭션(Transaction)은 데이터를 읽거나 쓰는 일을 원자적으로(전부 되거나 전부 안 되거나) 수행합니다.

DBMS가 하는 일

  1. 정의: 데이터 타입, 구조, 제약조건을 정함 (예: 학년은 1~5 중 하나)
  2. 구축: 초기 데이터를 HDD/SSD 같은 보조기억장치에 저장
  3. 조작: 검색(질의, 보고서), 수정(삽입·삭제·갱신), 웹 앱 등을 통한 접근
  4. 공유: 여러 사용자와 프로그램이 동시에 써도 데이터를 올바르게 유지

DB 설계 단계

DB 접근 방식의 4가지 특징

파일 처리 방식과 비교했을 때 DB 방식이 갖는 특징입니다. 시험에 자주 나오는 단골 주제입니다.

특징의미예시
(1) 자기 기술성 (Self-describing)DB 안에 데이터뿐 아니라 데이터의 구조·타입·제약조건 정의도 함께 저장. 이 정의를 메타데이터, 보관하는 곳을 카탈로그라 함“Course_number는 4글자+4숫자”라는 정보가 카탈로그에 있음
(2-1) 프로그램-데이터 독립성데이터 구조를 바꿔도 프로그램을 안 고쳐도 됨STUDENT에 Birth_date를 추가해도 SELECT class FROM Student는 그대로. C 구조체였다면 코드를 고쳐야 함
(2-2) 데이터 추상화저장 세부사항은 숨기고 개념적인 모습만 보여 줌. 이를 위한 도구가 데이터 모델데이터가 디스크 어디에 있는지 몰라도 됨
(3) 다중 뷰 지원사용자마다 관심 있는 부분만 다르게 보여 줌성적표 뷰, 선수과목 확인 뷰
(4) 데이터 공유와 다중 사용자 트랜잭션여러 사용자가 동시에 읽고 써도 동시성 제어가 정확성을 보장. 트랜잭션은 ACID를 만족해야 함OLTP: 항공 예약, 주식 거래, 수강신청
시험 포인트 ACID = Atomicity(원자성), Consistency(일관성), Isolation(고립성), Durability(지속성). 완료된 트랜잭션의 결과가 영구히 남도록 보장하는 것은 회복(Recovery) 서브시스템입니다.

DB 방식의 장점

  • 중복 제어: 같은 데이터를 한 곳에만 저장하는 것이 이상적(데이터 정규화). 다만 성능 때문에 일부러 중복을 두기도 함(통제된 중복).
  • 권한 없는 접근 제한: 보안·권한 서브시스템, 계정 생성은 DBA만.
  • 객체의 영속적 저장: 객체지향 DBMS는 프로그램 객체를 그대로 저장. 프로그래밍 언어 자료구조와 DBMS 자료구조가 안 맞는 문제를 임피던스 불일치라 함.
  • 효율적 질의 처리를 위한 저장 구조: 인덱스(트리·해시), DBMS 자체 버퍼 관리.
  • 그 밖에: 질의 최적화, 백업과 회복, 다양한 사용자 인터페이스, 복잡한 관계 표현, 무결성 제약조건 강제, 트리거를 이용한 추론과 동작.

DBMS를 쓰지 않는 게 나을 때

  • 초기 비용(하드웨어, 소프트웨어, 교육)과 보안·동시성·회복 기능의 오버헤드가 부담될 때
  • DB와 응용이 단순하고 바뀔 일이 없을 때, 여러 사용자가 접근하지 않을 때
  • 저장 공간이 작은 임베디드 시스템 (이럴 땐 SQLite)
  • 엄격한 실시간 요구, 모델링으로 표현하기 어려운 복잡한 데이터(유전체), DBMS가 지원하지 않는 특수 연산(GIS → 공간 DBMS, R-tree)

데이터 모델

데이터 모델은 데이터 추상화를 위한 도구로, DB의 구조(타입, 관계, 제약조건), 그 구조를 다루는 연산(기본 연산인 삽입·삭제·갱신과 COMPUTE_GPA 같은 사용자 정의 연산), 지켜야 할 제약조건을 설명하는 개념의 집합입니다.

범주특징예
개념적 (고수준)사용자가 데이터를 생각하는 방식과 가까움. 엔티티 기반ER 모델
표현적 (구현)고수준과 저수준의 중간. 상용 DBMS 대부분이 사용관계형 모델 (이 과목의 중심)
물리적 (저수준)저장 매체에 데이터가 어떻게 저장되는지레코드 형식(행/열 지향), 정렬 순서, 접근 경로(인덱스)
자기 기술적데이터 설명과 데이터 값을 함께 저장XML, JSON, 키-값 저장소, MongoDB

스키마 vs 상태

스키마 (Schema) = 설계도

DB에 대한 설명(메타데이터). 카탈로그에 저장. 설계할 때 정하고 거의 바뀌지 않음. 스키마의 구성 요소(STUDENT, COURSE)를 스키마 구조물(construct)이라 함.

상태 (State) = 그 순간의 실제 데이터

특정 시점에 DB에 저장된 실제 데이터 전체. 인스턴스, 스냅샷이라고도 함. DB가 갱신될 때마다 바뀜. 처음 넣은 상태 = 초기 상태, 구조와 제약조건을 모두 만족하는 상태 = 유효(valid) 상태.

3단계 스키마 구조 (Three-Schema Architecture)

목표는 사용자 응용과 물리적 DB를 분리하는 것. DB 방식의 특징 (1) 카탈로그, (2) 프로그램-데이터 독립성, (3) 다중 뷰를 지원하려고 제안되었습니다.

  • 내부 스키마: 물리적 저장 구조와 접근 경로. 물리적 데이터 모델 사용.
  • 개념 스키마: 전체 사용자 공동체를 위한 DB 전체의 구조·제약조건. ER 또는 관계형 모델 사용.
  • 외부 스키마: 사용자 그룹별 뷰. 관심 있는 부분만 보여 주고 나머지는 숨김. 한 그룹은 다른 그룹의 외부 스키마를 모름.

사용자의 요청은 외부 → 개념 → 내부 순서로 매핑(변환)되어 처리되고, 꺼낸 데이터는 다시 외부 요청에 맞게 재구성됩니다(예: SQL 결과를 웹 페이지 형태로).

데이터 독립성

한 단계의 스키마를 바꿔도 바로 위 단계의 스키마는 바꾸지 않아도 되는 능력입니다. 하위 스키마가 바뀌면 두 스키마 사이의 매핑만 고치면 됩니다.

논리적 데이터 독립성

개념 스키마를 바꿔도 외부 스키마와 응용 프로그램은 그대로. 예: 새 레코드 타입 추가, 제약조건 변경.

물리적 데이터 독립성

내부 스키마를 바꿔도 개념 스키마는 그대로. 예: 파일 구조 재구성, 성능을 위한 새 인덱스 생성.

헷갈림 주의 “무엇이 바뀌어도 무엇이 안 바뀌는가”로 외우세요. 논리적 = 개념이 바뀌어도 외부는 안전. 물리적 = 내부가 바뀌어도 개념은 안전. 일반적으로 물리적 독립성이 달성하기 더 쉽습니다.

DBMS 언어

DDL (데이터 정의어)

개념/내부 스키마와 그 매핑을 정의. 현대 관계형 DBMS에서는 저장 정의어(SDL), 뷰 정의어(VDL)가 따로 없고 SQL이 다 맡음.

CREATE TABLE Student (...)

DML (데이터 조작어)

검색과 갱신. 범용 언어(호스트 언어: C, Java, Python)에 끼워 넣을 수 있고, ODBC/JDBC 같은 라이브러리로도 접근.

SELECT * FROM Student

DBMS 구성 모듈과 분류

디스크에는 저장된 DB와 카탈로그가 있습니다. 디스크 접근은 OS가 담당하지만, 많은 DBMS는 성능 때문에 자체 버퍼 관리자를 둡니다(디스크 I/O를 줄이는 것이 성능에 결정적). 상위의 저장 데이터 관리자가 DB와 카탈로그의 디스크 접근을 제어합니다.

DBMS는 데이터 모델(계층·네트워크 → 관계형 → 객체·객체관계형 → NoSQL: 문서, 열, 그래프, 키-값), 사용자 수(단일/다중), 위치(중앙집중/분산: 동종·이종·연합), 비용(오픈소스/상용), 목적(범용/특수: OLAP, GIS)으로 분류됩니다. 디스크 기반과 인메모리 DB로도 나눕니다.

각 단순 속성에는 값 집합(도메인)이 있습니다(예: Age는 16~70 사이 정수). 기본 ER 다이어그램에는 보통 그리지 않습니다.

엔티티 타입 (내포, intension)

같은 속성을 가진 엔티티들의 “틀”. 스키마와 비슷. 예: EMPLOYEE. ER에서 사각형.

엔티티 집합 (외연, extension)

어느 시점에 DB에 있는 그 타입의 엔티티 전체. 상태와 비슷. 예: e1, e2, …

관계 (Relationship)

  • 관계: 둘 이상의 엔티티를 특정 의미로 연결. 예: “Alice는 GPT-5 프로젝트에서 일한다.”
  • 관계 타입: 같은 종류의 관계들의 묶음(WORKS_ON). 관계 인스턴스: r1 = (Alice, GPT-5). 관계 집합: R = {r1, r2, …}.
  • 차수(Degree): 참여하는 엔티티 타입의 수. 단항(재귀), 이항(2개), 삼항(3개).
  • 역할 이름: 엔티티가 관계에서 맡는 역할. 같은 엔티티 타입이 한 관계에 두 번 참여할 때 꼭 필요.
  • 재귀 관계: 같은 엔티티 타입끼리의 관계. SUPERVISION에서 EMPLOYEE는 감독자(supervisor) 역할과 피감독자(supervisee) 역할로 참여.

관계의 구조적 제약조건

“모든 직원은 정확히 한 부서에서 일한다”, “일부 직원만 부서를 관리한다” 같은 규칙을 그림에 표시하는 방법입니다.

① 카디널리티 비율 = 최대값

한 엔티티가 참여할 수 있는 관계 인스턴스의 최대 개수. 1:1, 1:N, N:1, M:N.

  • MANAGES (EMPLOYEE:DEPARTMENT) = 1:1
  • WORKS_FOR (EMPLOYEE:DEPARTMENT) = N:1
  • WORKS_ON (EMPLOYEE:PROJECT) = M:N

② 참여 제약조건 = 최소값

엔티티가 존재하려면 반드시 관계에 참여해야 하는가?

  • 전체 참여 (존재 종속): 모두 참여해야 함. 이중선. 예: 모든 직원은 부서에 속함.
  • 부분 참여 (기본값): 일부만 참여. 단일선. 예: 일부 직원만 부서를 관리.

(min, max) 표기법

엔티티 E가 관계 R에 최소 min번, 최대 max번 참여한다는 뜻으로 (min, max)를 씁니다. min = 0이면 부분 참여, min ≥ 1이면 전체 참여입니다. 항상 0 ≤ min ≤ max, max ≥ 1.

헷갈림 주의 (교수님이 강조한 부분)

카디널리티 비율은 “N명의 EMPLOYEE가 1개의 DEPARTMENT에 매핑된다”처럼 상대편 개수를 자기 쪽 선에 씁니다. 반면 (min, max)는 “이 엔티티 하나에서 관계선이 몇 개 나가는가”를 자기 옆에 씁니다. 부서 하나에서 선이 최소 4개, 최대 N개 → 부서 옆에 (4, N). 그래서 위치가 반대로 보입니다. (min, max) 표기에서는 min으로 참여 제약을 표현하므로 이중선을 굳이 그리지 않아도 됩니다.

요구사항 문장(min, max)

관계의 속성

관계 자체도 속성을 가질 수 있습니다. “Alice가 GPT-5에 주당 몇 시간 일하나?”의 Hours는 직원 혼자의 값도, 프로젝트 혼자의 값도 아니고 (직원, 프로젝트) 조합에서 나오는 값이죠. 그래서 관계 속성은 주로 M:N 관계에 붙습니다. 1:N 관계의 속성(예: WORKS_FOR의 Start_date)은 N쪽 엔티티로 옮길 수 있습니다. 1:1이면 어느 쪽으로 옮겨도 됩니다.

약한 엔티티 (Weak Entity)

  • 자기 키가 없는 엔티티 타입. 혼자서는 존재할 수 없음. 예: DEPENDENT(부양가족)는 직원이 없으면 의미가 없음.
  • 소유 엔티티(owner, parent)와 식별 관계로 연결됨 (EMPLOYEE —DEPENDENTS_OF— DEPENDENT).
  • 식별 방법 = 부분키(같은 소유자 안에서만 유일, 예: Dependent_name) + 소유자의 키(Ssn).
  • 약한 엔티티는 식별 관계에 항상 전체 참여. 단, 전체 참여(존재 종속)라고 해서 모두 약한 엔티티는 아님. 자기 키가 있으면 강한 엔티티.

COMPANY DB의 ER 다이어그램

요구사항: 회사는 부서들로 구성 (부서명·번호 유일, 관리자 1명과 관리 시작일, 위치 여러 곳). 부서는 프로젝트들을 관리 (프로젝트명·번호 유일, 위치 1곳). 직원은 한 부서에서 일하지만 여러 프로젝트에 참여, 프로젝트별 주당 시간과 직속 감독자를 기록. 직원은 부양가족을 가질 수 있음.

처음 설계에서는 “부서의 Manager”, “직원의 Department”, “직원의 Supervisor” 같은 것을 속성으로 두지만, 다른 엔티티를 가리키는 속성은 관계로 바꿉니다. 그 결과 6개의 이항 관계가 나옵니다: WORKS_FOR, MANAGES, CONTROLS, WORKS_ON, SUPERVISION, DEPENDENTS_OF. 같은 두 엔티티 사이에도 의미가 다르면 관계가 여러 개일 수 있습니다(MANAGES와 WORKS_FOR).

04관계형 데이터 모델과 제약조건

Chapter 5 · E. F. Codd, 1970

1970년 E. F. Codd가 논문 “A Relational Model for Large Shared Data Banks”로 제안했고, 단순함과 수학적 기반 덕분에 혁명을 일으켜 튜링상을 받았습니다. 첫 상용 구현은 1980년대 초 IBM SQL/DS와 Oracle입니다. 관계형 모델은 DB를 릴레이션(=표)들의 모음으로 봅니다.

용어 대응표

일상 용어 (비공식)정식 용어설명
테이블릴레이션 (Relation)튜플들의 집합

열에 올 수 있는 모든 값도메인 (Domain)원자값들의 집합 + 데이터 타입/형식
행 (Row)튜플 (Tuple)값들의 순서 있는 목록 <v1, …, vn>
테이블 정의릴레이션 스키마 (내포)R(A1, A2, …, An)
데이터가 채워진 테이블릴레이션 상태 (외연)r(R) = {t1, t2, …, tm}
  • 차수(degree, arity) = 속성의 개수. CUSTOMER(Cust-id, Cust-name, Addr, Phone#)의 차수는 4, 튜플 하나는 4-튜플.
  • 릴레이션 상태는 도메인들의 카티션 곱의 부분집합: r(R) ⊆ dom(A1) × dom(A2) × … × dom(An).
  • 예: dom(A1) = {0, 1}, dom(A2) = {a, b, c}이면 카티션 곱은 6개 조합이고, r(R) = {<0,a>, <0,b>, <1,a>, <1,b>}는 가능한 상태 중 하나 (2-튜플 4개).
  • 표기: t[Name] 또는 t.Name = 튜플 t의 Name 값. t[Ssn, Gpa, Age] = 부분 튜플. R.A = 릴레이션 R의 속성 A.
  • 대리키(surrogate key): 행을 구분하려고 만든 인공 번호(예: Reg_No 1, 2, 3).

릴레이션의 특성

항목순서가 있나?이유
튜플(행)의 순서없음릴레이션은 집합. 행 순서를 바꿔도 같은 릴레이션
속성(열)과 튜플 안 값의 순서있음n-튜플은 정의상 순서 있는 목록. 단, (속성 이름, 값) 쌍으로 정의하면 순서 없음 (자기 기술적 튜플)
  • 모든 값은 원자값: 복합 속성·다중값 속성 불가 (평면 관계 모델, 제1정규형 가정). 복합 → 단순 속성들로 쪼개고, 다중값 → 별도 릴레이션으로.
  • 각 값은 해당 속성의 도메인에서 와야 함.
  • NULL의 세 가지 의미: ① 모름(Unknown, 값이 있는데 모르거나 있는지조차 모름), ② 제공 안 됨(Not available, 있지만 일부러 숨김, 예: 사생활 보호), ③ 해당 없음(Inapplicable, 예: 사무실이 없는 학생의 사무실 전화).

제약조건의 세 범주

범주설명예
1. 내재적 (모델 기반)데이터 모델 자체의 성질관계형 모델은 속성 값으로 리스트를 허용 안 함
2. 명시적 (스키마 기반)스키마에 직접 표현. 이번 장의 중심도메인, 키, 엔티티 무결성, 참조 무결성
3. 의미적 (응용 기반, 업무 규칙)모델로 표현 못 함 → 응용 프로그램, 트리거, 어서션으로“나이 > 65이고 근무 > 40시간이면 임금 2배”

도메인 제약조건

튜플의 모든 값은 그 속성의 도메인에 속해야 합니다(허용되면 NULL 가능).

키 제약조건: 슈퍼키, 키, 후보키, 기본키

릴레이션은 집합이므로 모든 튜플은 서로 달라야 합니다.

  • 슈퍼키(SK): 어떤 유효한 상태에서도 두 튜플이 같은 값을 갖지 않는 속성들의 부분집합 (유일성).
  • 키: 최소한의 슈퍼키. 속성을 하나라도 빼면 더 이상 슈퍼키가 아님 (최소성).
  • 후보키: 키가 여러 개일 때 각각을 후보키라 부름. 그중 하나를 골라 기본키(PK)로 지정(밑줄). 나머지는 유일키(SQL의 UNIQUE).
  • PK 선택 규칙: 보통 속성 개수가 가장 적은 후보키를 고름. 하지만 설계자 판단.
시험 포인트: 자주 나오는 질문
  • 슈퍼키는 키인가? → 아니다. 최소일 때만 키. 반대로 모든 키는 슈퍼키.
  • {VIN, Make}는? → 슈퍼키이지만 키는 아님 (Make를 빼도 VIN만으로 유일).
  • {State, Reg#}는? → 키이면서 슈퍼키.
  • 키를 포함한 속성 집합은 왜 항상 슈퍼키? → 키만으로 이미 유일하니까 뭘 더 붙여도 유일.

엔티티 무결성 제약조건

기본키 값은 NULL이 될 수 없습니다. PK가 여러 속성으로 되어 있으면 그중 어느 것도 NULL이면 안 됩니다. PK로 튜플을 구별하는데 NULL이면 구별할 수 없기 때문입니다. PK가 아닌 속성의 NULL 허용 여부는 따로 정합니다.

참조 무결성 제약조건

지금까지의 제약은 릴레이션 하나에만 적용됐지만, 참조 무결성은 두 릴레이션 사이의 일관성을 지킵니다. 참조하는 릴레이션 R1의 외래키(FK)는 참조되는 릴레이션 R2의 PK를 가리키고, FK 값은 다음 둘 중 하나여야 합니다.

  1. R2에 실제로 존재하는 PK 값 (t1[FK] = t2[PK])
  2. NULL (아직 지정 안 됨). 단, 그 FK가 R1의 PK 일부라면 NULL 불가 (엔티티 무결성 위반이 되므로)

COMPANY 관계형 스키마 (모든 PK와 FK)

관계형 DB 스키마 S = {R1, …, Rn} + 무결성 제약조건(IC) 집합. 관계형 DB 상태는 모든 릴레이션 상태의 모음이고, IC를 만족하지 않으면 무효(invalid) 상태입니다. 튜플을 삽입·삭제·갱신할 때마다 새 상태가 만들어집니다.

갱신 연산과 제약조건 위반

위반이 생기면 DBMS가 할 수 있는 일: ① 연산 거부 (RESTRICT / NO ACTION / REJECT, 대부분의 기본값), ② 수행하고 알리기 (거의 안 씀), ③ 추가 갱신으로 바로잡기 (CASCADE, SET NULL, SET DEFAULT: 참조되는 쪽 → 참조하는 쪽으로 전파), ④ 사용자 정의 오류 처리 루틴 실행.

연산위반 가능한 제약조건

DELETE참조 무결성만 (지우는 튜플을 다른 튜플이 FK로 가리키고 있을 때). 대처: RESTRICT, CASCADE, SET NULL/DEFAULT
UPDATE일반 속성: 도메인, NOT NULL. PK를 바꾸면 “삭제 + 삽입”과 같아서 키·엔티티·참조 무결성 모두. FK를 바꾸면 참조 무결성

스키마와 카탈로그

  • SQL 스키마: 같은 DB에 속한 테이블·제약조건·뷰·도메인 등을 묶는 단위. 스키마 이름 + 소유자(권한 식별자). CREATE SCHEMA COMPANY AUTHORIZATION 'Joshua';

CREATE TABLE EMPLOYEE (
  Fname VARCHAR(15) NOT NULL,
  Minit CHAR,
  Lname VARCHAR(15) NOT NULL,
  Ssn CHAR(9) NOT NULL,
  Bdate DATE,
  Address VARCHAR(30),
  Sex CHAR,
  Salary DECIMAL(10,2),
  Super_ssn CHAR(9),
  Dno INT,
  PRIMARY KEY (Ssn)
);
CREATE TABLE DEPARTMENT (
  Dname VARCHAR(15) NOT NULL,
  Dnumber INT NOT NULL,
  Mgr_ssn CHAR(9) NOT NULL,
  Mgr_start_date DATE,
  PRIMARY KEY (Dnumber),
  UNIQUE (Dname),
  FOREIGN KEY (Mgr_ssn) REFERENCES EMPLOYEE(Ssn) ON DELETE SET NULL
);
CREATE TABLE WORKS_ON (
  Essn CHAR(9) NOT NULL,
  Pno INT NOT NULL,
  Hours DECIMAL(3,1),
  PRIMARY KEY (Essn, Pno),
  FOREIGN KEY (Essn) REFERENCES EMPLOYEE(Ssn) ON DELETE CASCADE,
  FOREIGN KEY (Pno) REFERENCES PROJECT(Pnumber) ON DELETE CASCADE
);

ALTER TABLE EMPLOYEE ADD FOREIGN KEY (Dno) REFERENCES DEPARTMENT(Dnumber);
시험 포인트: 왜 EMPLOYEE의 FK는 처음에 빠져 있나?

① 순환 참조: EMPLOYEE.Dno → DEPARTMENT, DEPARTMENT.Mgr_ssn → EMPLOYEE. ② 아직 만들어지지 않은 테이블을 참조하면 오류(EMPLOYEE를 만들 때 DEPARTMENT가 없음). 그래서 테이블을 먼저 만들고 ALTER TABLE로 FK를 추가합니다. 데이터 삽입도 같은 이유로 순서가 중요합니다: 실습에서는 EMPLOYEE 몇 명을 Dno = NULL로 넣고 → DEPARTMENT 삽입 → UPDATE로 Dno 채우기 → 나머지 테이블 순서로 넣었습니다.

SELECT-FROM-WHERE 기본 구조

SELECT  <속성 목록>     -- 무엇을 보여 줄까 (projection)

WHERE   <조건>;         -- 어떤 행만 남길까 (selection + join 조건)

중복과 집합 연산

SQL은 중복을 자동으로 제거하지 않습니다. 이유: ① 중복 제거는 정렬이 필요해서 비쌈, ② 사용자가 중복을 보고 싶을 수 있음, ③ 집계 함수(SUM, AVG 등)에서는 보통 중복을 지우면 안 됨. 지우고 싶으면 SELECT DISTINCT.

SELECT ALL Salary FROM EMPLOYEE;       -- 25000이 세 번 나옴
SELECT DISTINCT Salary FROM EMPLOYEE;  -- 25000은 한 번만

집합 연산: UNION(합), EXCEPT(차, Oracle은 MINUS), INTERSECT(교). 이것들은 결과의 중복을 제거하고, UNION ALL 등 ALL을 붙이면 멀티셋 연산입니다. 두 결과는 타입 호환(같은 속성, 같은 순서)이어야 합니다.

-- 'Smith'가 작업자이거나, 프로젝트를 관리하는 부서의 관리자인 프로젝트 번호
(SELECT DISTINCT Pnumber
 FROM PROJECT, DEPARTMENT, EMPLOYEE
 WHERE Dnum = Dnumber AND Mgr_ssn = Ssn AND Lname = 'Smith')
UNION
(SELECT DISTINCT Pnumber
 FROM PROJECT, WORKS_ON, EMPLOYEE
 WHERE Pnumber = Pno AND Essn = Ssn AND Lname = 'Smith');

LIKE, 산술, BETWEEN, ORDER BY

  • % = 0개 이상의 아무 문자, _ = 정확히 한 문자. Address LIKE '%Houston,TX%'. 문자 자체를 찾으려면 이스케이프 문자를 지정(ESCAPE '\').
  • SELECT에서 + - * / 사용 가능: SELECT 1.1 * Salary AS Increased_sal.
  • Salary BETWEEN 30000 AND 40000은 양 끝을 포함(≥ 30000 AND ≤ 40000).
  • ORDER BY는 맨 끝. 기본은 ASC(오름차순), DESC는 내림차순.
-- ProductX 참여 직원의 급여를 10% 올리면?
SELECT E.Fname, E.Lname, 1.1 * E.Salary AS Increased_sal
FROM EMPLOYEE E, WORKS_ON W, PROJECT P
WHERE E.Ssn = W.Essn AND W.Pno = P.Pnumber AND P.Pname = 'ProductX';

NULL은 모름 / 제공 안 됨 / 해당 없음 중 어떤 뜻인지 SQL이 구분하지 못합니다. 그래서 NULL이 끼인 비교 결과는 TRUE도 FALSE도 아닌 UNKNOWN이 됩니다. 결과는 TRUE, FALSE, UNKNOWN 셋 중 하나입니다.

NOT TRUE = FALSE, NOT FALSE = TRUE, NOT UNKNOWN = UNKNOWN. 외우는 요령: AND는 FALSE가 하나라도 있으면 FALSE, OR는 TRUE가 하나라도 있으면 TRUE, 나머지 애매한 건 UNKNOWN.

WHERE 절은 TRUE인 튜플만 고릅니다(UNKNOWN은 탈락). 그래서 NULL 검사는 = NULL이 아니라 IS NULL / IS NOT NULL로 합니다.

SELECT Fname, Lname FROM EMPLOYEE WHERE Super_ssn IS NULL;   -- 결과: James Borg

중첩 질의 (Nested Query)

WHERE 안에 또 하나의 완전한 SELECT 블록(서브쿼리, 내부 질의)을 넣는 것입니다.

  • v IN V: v가 집합 V의 원소면 TRUE. 튜플끼리도 비교 가능: (Pno, Hours) IN (SELECT Pno, Hours …)
  • = ANY(= = SOME)는 IN과 같음. > ALL은 “모든 값보다 크다”.
  • 명시적 집합: WHERE Pno IN (1, 2, 3)
-- 5번 부서의 모든 직원보다 급여가 많은 직원
SELECT Lname, Fname
FROM EMPLOYEE
WHERE Salary > ALL (SELECT Salary FROM EMPLOYEE WHERE Dno = 5);

상관 중첩 질의 (Correlated Nested Query)

내부 질의가 외부 질의의 속성(아래의 E.Fname, E.Sex)을 참조하면, 외부 튜플 하나마다 내부 질의가 한 번씩 평가됩니다. 모호함을 피하려면 모든 테이블에 별칭을 다세요.

-- 자기와 이름도 같고 성별도 같은 부양가족이 있는 직원
SELECT E.Fname, E.Lname
FROM EMPLOYEE E
WHERE E.Ssn IN (SELECT D.Essn FROM DEPENDENT D
                WHERE E.Fname = D.Dependent_name AND E.Sex = D.Sex);
-- '=' 또는 IN을 쓰는 중첩 질의는 조인 하나로 바꿔 쓸 수 있다
SELECT E.Fname, E.Lname
FROM EMPLOYEE E, DEPENDENT D
WHERE E.Ssn = D.Essn AND E.Sex = D.Sex AND E.Fname = D.Dependent_name;

EXISTS와 NOT EXISTS

EXISTS (서브쿼리)는 결과가 한 행이라도 있으면 TRUE, NOT EXISTS는 결과가 비어 있으면 TRUE입니다.

-- 부양가족이 한 명 이상 있는 관리자
SELECT Fname, Lname
FROM EMPLOYEE
WHERE EXISTS (SELECT * FROM DEPENDENT WHERE Ssn = Essn)
  AND EXISTS (SELECT * FROM DEPARTMENT WHERE Ssn = Mgr_ssn);
쉽게 말하면: “모든 ~”은 이중 부정으로

SQL에는 “모든(∀)”이 없습니다. 그래서 “5번 부서의 모든 프로젝트에 참여하는 직원”을 “5번 부서 프로젝트 중에 참여 안 한 것이 없는 직원”으로 바꿉니다. (…하지 않은 튜플이 존재하지 않는다 → …한 튜플만 존재한다)

SELECT Fname, Lname
FROM EMPLOYEE
WHERE NOT EXISTS ( (SELECT Pnumber FROM PROJECT WHERE Dnum = 5)
                   EXCEPT
                   (SELECT Pno FROM WORKS_ON WHERE Ssn = Essn) );
-- 5번 부서 프로젝트 집합 − 내가 참여한 프로젝트 집합 = 공집합이면 선택

조인된 테이블과 외부 조인

FROM 절에 조인 결과 자체를 테이블처럼 쓸 수 있습니다.

SELECT Fname, Lname, Address
FROM (EMPLOYEE JOIN DEPARTMENT ON Dno = Dnumber)      -- INNER JOIN과 같음
WHERE Dname = 'Research';

-- NATURAL JOIN: 이름이 같은 속성끼리 자동으로 동등 조인. 이름이 다르면 먼저 이름을 바꿔야 함
SELECT Fname, Lname, Address
FROM (EMPLOYEE NATURAL JOIN (DEPARTMENT AS DEPT (Dname, Dno, Mssn, Msdate)))
WHERE Dname = 'Research';
  • INNER JOIN(기본): 짝이 있는 튜플만.
  • LEFT OUTER JOIN: 왼쪽 테이블의 모든 튜플. 짝이 없으면 오른쪽 속성은 NULL. RIGHT는 반대.
  • FULL OUTER JOIN: LEFT와 RIGHT 결과를 합친 것.
  • JOIN을 중첩하면 다중 조인(multiway join)도 가능.
SELECT E.Lname AS Employee_name, S.Lname AS Supervisor_name
FROM EMPLOYEE E LEFT OUTER JOIN EMPLOYEE S ON E.Super_ssn = S.Ssn;

집계 함수와 그룹화

여러 튜플을 하나의 요약값으로: COUNT, SUM, MAX, MIN, AVG, MEDIAN. SELECT 절과 HAVING 절에 쓸 수 있습니다.

SELECT SUM(Salary), MAX(Salary), MIN(Salary), AVG(Salary) FROM EMPLOYEE;
SELECT COUNT(*) FROM EMPLOYEE, DEPARTMENT WHERE Dno = Dnumber AND Dname = 'Research';  -- 4
SELECT COUNT(DISTINCT Salary) FROM EMPLOYEE;                                          -- 6
헷갈림 주의: 집계와 NULL COUNT(*)는 행 수를 세므로 NULL이 있어도 셉니다. 하지만 COUNT(속성), SUM, AVG, MAX, MIN은 그 속성이 NULL인 값은 버리고 계산합니다.

GROUP BY와 HAVING

  • GROUP BY: 그룹 속성 값이 같은 튜플끼리 묶고, 그룹마다 집계 함수 적용.
  • 그룹 속성은 SELECT 절에도 나와야 합니다 (교수님 강조 사항).
  • HAVING: 그룹 전체를 고르거나 버리는 조건. WHERE는 그룹을 만들기 전 개별 튜플에 적용.
  • 조인 결과에도 GROUP BY를 적용할 수 있음.
SELECT Dno, COUNT(*), AVG(Salary) FROM EMPLOYEE GROUP BY Dno;
-- (5, 4, 33250) (4, 3, 31000) (1, 1, 55000)

SELECT Pnumber, Pname, COUNT(*)
FROM PROJECT, WORKS_ON
WHERE Pnumber = Pno
GROUP BY Pnumber, Pname
HAVING COUNT(*) > 2;      -- 참여 직원이 2명 이하인 ProductX, ProductZ는 탈락
시험 포인트: Q28 (WHERE와 HAVING의 함정)

“직원이 2명 이상인 부서마다, 급여가 40,000 넘는 직원 수를 구하라.”

-- 틀린 풀이: WHERE가 먼저 적용돼서 '고액 연봉자가 2명 이상인 부서'를 구해 버림
SELECT Dno, COUNT(*) FROM EMPLOYEE
WHERE Salary > 40000
GROUP BY Dno HAVING COUNT(*) >= 2;

-- 맞는 풀이: 부서 크기 조건은 중첩 질의로 따로
SELECT Dno, COUNT(*) FROM EMPLOYEE
WHERE Salary > 40000
  AND Dno IN (SELECT Dno FROM EMPLOYEE GROUP BY Dno HAVING COUNT(*) >= 2)
GROUP BY Dno;
-- 결과: (4, 1)  ← 4번 부서의 Wallace 43000. 5번 부서 Wong은 40000이라 '초과' 아님

WITH, CASE, 재귀 질의

-- WITH: 이 질의에서만 쓰는 임시 테이블 (인라인 뷰)
WITH BIGDEPTS (Dno) AS
  (SELECT Dno FROM EMPLOYEE GROUP BY Dno HAVING COUNT(*) >= 2)
SELECT Dno, COUNT(*)
FROM EMPLOYEE
WHERE Salary > 40000 AND Dno IN (SELECT Dno FROM BIGDEPTS)
GROUP BY Dno;

-- CASE: 조건에 따라 값이 달라질 때. 질의, 삽입, 갱신 어디서든 값 자리에 사용
UPDATE EMPLOYEE
SET Salary = CASE WHEN Dno = 5 THEN Salary + 2000
                  WHEN Dno = 4 THEN Salary + 1500
                  WHEN Dno = 1 THEN Salary + 3000
                  ELSE Salary + 0 END;

-- 재귀 질의: 감독자-직원 관계를 끝까지 따라가기 (SQL99 표준)
WITH RECURSIVE SUP_EMP (SupSsn, EmpSsn) AS
  ( SELECT Super_ssn, Ssn FROM EMPLOYEE
    UNION
    SELECT S.EmpSsn, E.Ssn FROM EMPLOYEE E, SUP_EMP S WHERE E.Super_ssn = S.EmpSsn )
SELECT * FROM SUP_EMP;

뷰 (View, 가상 테이블)

뷰는 다른 테이블에서 유도된 하나의 가상 테이블입니다. 실제로 저장되어 있지 않을 수 있습니다. 자주 쓰는 복잡한 조인을 뷰로 정의해 두면 단일 테이블처럼 조회할 수 있습니다.

CREATE VIEW WORKS_ON1 AS
  SELECT Fname, Lname, Pname, Hours
  FROM EMPLOYEE, PROJECT, WORKS_ON
  WHERE Ssn = Essn AND Pno = Pnumber;           -- 속성 이름은 원래 테이블에서 물려받음

CREATE VIEW DEPT_INFO (Dept_name, No_of_emps, Total_sal) AS   -- 새 이름을 1:1로 지정
  SELECT Dname, COUNT(*), SUM(Salary)
  FROM DEPARTMENT, EMPLOYEE
  WHERE Dnumber = Dno
  GROUP BY Dname;

SELECT Fname, Lname FROM WORKS_ON1 WHERE Pname = 'ProductX';
DROP VIEW WORKS_ON1;

장점: ① 질의 작성이 간단해짐, ② 보안·권한 부여 수단(예: 5번 부서 직원 정보만 보이는 뷰에만 권한을 줌), ③ 구체화하면 비싼 조인 비용을 공간으로 절약.

뷰는 항상 최신이어야 합니다. 기본 테이블이 바뀌면 뷰에 자동 반영되어야 하고, 그 책임은 사용자가 아니라 DBMS에 있습니다. 뷰는 정의할 때가 아니라 질의할 때 실체화됩니다.

구현 전략방법단점·특징
① 질의 수정 (Query modification)뷰를 저장하지 않고, 뷰에 대한 질의를 기본 테이블에 대한 질의로 변환해서 그때그때 계산복잡한 뷰에 짧은 시간 안에 질의가 여러 번 오면 비효율적
② 뷰 구체화 (View materialization)처음 질의될 때 임시 뷰 테이블을 물리적으로 만들어 보관기본 테이블이 바뀔 때 뷰를 갱신하는 효율적 전략 필요 → 점진적 갱신(바뀐 부분만 반영). 한동안 질의가 없으면 자동 삭제

구체화 뷰의 갱신 시점: 즉시 갱신(기본 테이블이 바뀌자마자, write-through와 비슷), 지연 갱신(뷰 질의가 올 때, write-back과 비슷), 주기적 갱신(정해진 주기마다, 최신이 아닐 수 있음. 월별 매출, 인구 조사 등).

뷰 갱신 (View Update)

  • 단일 테이블에 정의되고 집계 함수가 없는 뷰의 갱신은 기본 테이블 갱신으로 바꿀 수 있음 → 대체로 가능.
  • 여러 테이블 조인 뷰는 기본 테이블에 반영하는 방법이 여러 가지라 모호함. 예: WORKS_ON1에서 John Smith의 Pname을 ProductX → ProductY로 바꾸면, WORKS_ON의 Pno를 바꿀지 PROJECT의 이름을 바꿀지 알 수 없음.
  • 집계 함수·그룹화 뷰는 갱신 불가. DEPT_INFO의 Total_sal을 100000으로 바꾸라고 하면 어느 직원 급여를 얼마나 바꿀지 정할 수 없음.

어서션 (Assertion)

키, 엔티티, NOT NULL, 참조 무결성 어디에도 안 맞는 일반적인 제약을 선언적으로 지정합니다. 조건을 위반하는 튜플을 찾는 질의를 쓰고, 그 결과가 비어 있어야(NOT EXISTS) 한다고 선언합니다. 단일 속성이나 도메인은 CHECK로 충분할 때 쓰지 말고, 그걸로 안 될 때만 씁니다. Oracle은 미지원.

-- 직원 급여는 그 직원이 속한 부서 관리자의 급여보다 많을 수 없다
CREATE ASSERTION SALARY_CONSTRAINT
CHECK ( NOT EXISTS ( SELECT *
                     FROM EMPLOYEE E, EMPLOYEE M, DEPARTMENT D
                     WHERE E.Salary > M.Salary AND E.Dno = D.Dnumber AND D.Mgr_ssn = M.Ssn ) );

트리거 (Trigger)

특정 사건이 일어나고 조건이 맞을 때 정해진 동작을 자동으로 실행하는 규칙입니다. 그래서 ECA 규칙이라고 부릅니다. 예: “출장비 한도를 넘으면 관리자에게 알림”, “부서 인원이 한도를 넘으면 새 직원을 받지 않음”.

-- 실습 6-1: 급여가 100,000을 넘으면 거부 (변경 '전'에 막아야 하므로 BEFORE)
CREATE TRIGGER SALARY_VIOLATION
BEFORE INSERT OR UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
BEGIN
  IF :NEW.Salary > 100000 THEN
    DBMS_OUTPUT.PUT_LINE('Error: Salary cannot exceed 100,000 for employee with SSN: ' || :NEW.Ssn);
    RAISE_APPLICATION_ERROR(-20001, 'Salary cannot exceed 100,000');
  END IF;
END;
/
-- 실습 6-2: 급여 변경 이력 남기기 (변경 '후'에 기록하므로 AFTER, 조건 없음)
CREATE TABLE Salary_Change_Log (Ssn CHAR(9), Old_Salary NUMBER(10,2),
                                New_Salary NUMBER(10,2), Change_Date TIMESTAMP);
CREATE TRIGGER trg_salary_change
AFTER UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
BEGIN
  INSERT INTO Salary_Change_Log VALUES (:OLD.Ssn, :OLD.Salary, :NEW.Salary, SYSTIMESTAMP);
END;
/
  • :OLD = 변경 전 값, :NEW = 변경 후(새로 들어오는) 값.
  • FOR EACH ROW = 영향받는 행마다 한 번씩 실행.
  • BEFORE 트리거에서 거부하면 갱신 자체가 일어나지 않음 (100,000은 성공, 100,001은 실패하고 값도 그대로).

DEPARTMENT 옆에 (4, N). 직원 쪽은 “직원은 정확히 한 부서” → EMPLOYEE 옆에 (1, 1).
약한 엔티티 DEPENDENT의 PK는? 그리고 식별 관계에서의 참여는?
PK = {Essn, Dependent_name} (소유자 PK + 부분키). 식별 관계에 항상 전체 참여.
CAR(State, Reg#, VIN, Make, Model, Year)에서 {VIN, Make}는 키인가, 슈퍼키인가?
슈퍼키이지만 키는 아니다. Make를 빼도 {VIN}만으로 유일하므로 최소성을 만족하지 않음.
엔티티 무결성 제약조건이란?
기본키 값은 NULL이 될 수 없다. 복합 PK라면 어느 구성 속성도 NULL이면 안 된다.
Dno = 7인 직원을 INSERT했다. 7번 부서는 없다. 어떤 제약 위반이고 기본 처리 방식은?
참조 무결성 위반. 기본적으로 거부(RESTRICT).
DELETE 연산이 위반할 수 있는 제약은? 대처 옵션 세 가지는?
참조 무결성만. RESTRICT(거부), CASCADE(참조하는 튜플도 삭제), SET NULL / SET DEFAULT(참조하는 FK를 NULL 또는 기본값으로).
1:N 관계 CONTROLS(DEPARTMENT 1 : PROJECT N)는 어떻게 매핑하나?
N쪽 PROJECT에 DEPARTMENT의 PK를 FK(Dnum)로 추가.
다중값 속성 Locations는 어떻게 매핑하나?
새 릴레이션 DEPT_LOCATIONS(Dnumber, Dlocation). Dnumber는 DEPARTMENT를 참조하는 FK, PK는 {Dnumber, Dlocation}.
COMPANY의 CREATE TABLE에서 EMPLOYEE의 FK를 처음부터 못 넣는 이유는?
순환 참조(EMPLOYEE ↔ DEPARTMENT, EMPLOYEE.Super_ssn → EMPLOYEE)와 아직 생성되지 않은 테이블(DEPARTMENT)을 참조하기 때문. 나중에 ALTER TABLE로 추가.
SQL이 결과의 중복을 자동으로 없애지 않는 이유 세 가지는?
① 중복 제거는 정렬이 필요해 비용이 큼, ② 사용자가 중복을 보고 싶을 수 있음, ③ 집계 함수 계산에서는 중복을 지우면 안 되는 경우가 많음.
Salary가 NULL인 직원이 있을 때 WHERE Salary > 30000 OR Salary <= 30000 의 결과에 그 직원이 나오나?
안 나온다. 두 비교 모두 UNKNOWN이고 UNKNOWN OR UNKNOWN = UNKNOWN. WHERE는 TRUE인 튜플만 고른다.
“5번 부서의 모든 프로젝트에 참여하는 직원”은 SQL로 어떻게 표현하나?
NOT EXISTS (5번 부서 프로젝트 집합 EXCEPT 내가 참여한 프로젝트 집합). “참여 안 한 프로젝트가 존재하지 않는다”는 이중 부정.
LEFT OUTER JOIN과 INNER JOIN의 결과 차이를 COMPANY의 직원-감독자 예로 설명하면?
INNER JOIN은 감독자가 있는 7명만 나오고, LEFT OUTER JOIN은 감독자가 없는 Borg까지 8명이 나오며 Borg의 감독자 칸은 NULL.
뷰 구현의 두 전략과 각각의 약점은?
질의 수정: 매번 기본 테이블로 변환해 계산 → 복잡한 뷰를 자주 조회하면 비효율. 뷰 구체화: 뷰 테이블을 저장 → 기본 테이블 변경 시 점진적 갱신 전략 필요.
DEPT_SUMMARY(GROUP BY 뷰)에 UPDATE를 하면?
오류. 집계·그룹화된 뷰는 기본 테이블의 어떤 행을 어떻게 바꿀지 정할 수 없어 갱신 불가.
트리거의 세 구성 요소는? 급여 상한 검사는 BEFORE와 AFTER 중 무엇?
Event, Condition, Action (ECA 규칙). 잘못된 값을 막아야 하므로 BEFORE. 변경 이력 기록은 AFTER.
